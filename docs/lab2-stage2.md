# ЛР2, этап 2: данные, контракты и схема PostgreSQL

Подготовка второго этапа выполнена 18 октября 2026 года. Прикладной MCP-сервер,
клиент, кнопки и новые команды Telegram относятся к следующим этапам.
[Спецификация](../spec.md) и [план](../plan.md) задают полный объём ЛР2.

## Зависимости

В окружении Python 3.12 сохранены версии библиотек ЛР1 и установлены
`mcp==2.3.0`, `pydantic==2.13.5`, `jsonschema==4.26.0`, `tzdata==2026.5`.
Прямые зависимости находятся в `requirements.txt`, проверенные транзитивные
версии — в `constraints.txt`; `pywin32` закреплён условно для Windows.

Выбор SDK проверен по [официальному релизу PyPI](https://pypi.org/project/mcp/2.3.0/)
и фактически установленному Python API. Структуры SDK принимают канонические
схемы и `structuredContent`; прикладная `_meta` сериализуется отдельно от
аргументов модели. Это проверка совместимости типов, а не готовое MCP-соединение.
Документация ветки `main` может отличаться от закреплённого релиза; следующие
этапы должны использовать API установленной версии.

Установка из корня проекта:

```bash
source scripts/env.sh
python -m pip install -r requirements-dev.txt
python -m pip check
```

## Расписание и контракты

[Учебное расписание](../data/schedule.json) вымышлено и покрывает
12–25 октября 2026 года, включая явно свободные дни. Оно подходит для фиксированного
времени обязательного эксперимента. Вне покрытия сервис сообщает отсутствие данных,
а не отсутствие занятий.

[Контракты](../app/mcp/contracts.py) описывают аргументы, результаты погоды,
расписания и напоминаний, ошибки, недельный ресурс и решение агента. Лишние поля
запрещены. Модель не может передать владельца, capability, SQL, URL или путь к файлу.
Проверка нового напоминания принимает доверенные часы и IANA-зону, отклоняет
прошлое время, несовпадение смещения и неоднозначные/несуществующие моменты DST.
Квитанция уже выполненного действия не должна проходить повторную проверку будущего.

[Сервис расписания](../app/mcp/schedule.py) загружает только путь из конфигурации,
проверяет файл целиком, лимит 1 МиБ, покрытие и совпадение зоны. Даты недели
определяются по переданным часам в зоне расписания; системные часы менять не нужно.
Он пока используется в тестах и не подключён к Telegram.

## Настройки

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `SCHEDULE_FILE` | `data/schedule.json` | Путь администратора к локальному файлу |
| `SCHEDULE_TIMEZONE` | `Europe/Moscow` | IANA-зона расписания |
| `MCP_TIMEOUT_SECONDS` | `15` | Будущий тайм-аут MCP, диапазон 1–60 секунд |
| `AGENT_TIMEOUT_SECONDS` | `135` | Будущий общий дедлайн, диапазон 1–300 секунд |
| `LLM_TOOL_MODE` | `native` | Будущий механизм выбора: `native` или `structured` |

Настройки проверяются `Settings`, примеры находятся в `.env.example`; стартовый
скрипт и Compose передают те же значения. Наличие файла проверяет сервис данных,
а не загрузчик всех настроек. Это позволяет проверять конфигурацию независимо
от файлов расписания и состояния MCP.

Личное расписание при необходимости подключается отдельным локальным файлом,
например `.tools/schedule-personal.json`, через `SCHEDULE_FILE` в `.env`.
Этот путь уже исключён из Git. При подключении к модели запрошенная часть
расписания будет передаваться через OpenRouter для формирования ответа.
Docker и архив автоматического деплоя включают только вымышленный
`data/schedule.json`; остальные файлы `data/` или произвольный личный путь
не упаковываются. Автоматический cloud-deploy с другим `SCHEDULE_FILE`
останавливается до удалённых действий и объясняет ограничение.

## PostgreSQL

Новая [миграция 006](../app/migrations/006_agent_state.sql) добавляет:

- `labbi_users.timezone` и отдельный `confirmation_epoch`;
- `labbi_agent_requests` — идентичность исходных сообщений независимо от истории;
- `labbi_actions` — параметры, срок, состояние, хеш capability и квитанцию;
- `labbi_reminders` — одно напоминание на подтверждённое действие;
- `labbi_agent_events` — аудит своего решения, счётчики вызовов и длительность.

Уникальные ограничения и составные внешние ключи связывают владельца,
исходное сообщение, действие, параметры и квитанцию. Одна активная карточка
разрешена на владельца. Напоминание и состояние `committed` согласуются одной
транзакцией с отложенными внешними ключами. Старые миграции `001`–`005` сохранены.

Схема не заменяет прикладное подтверждение: проверка времени непосредственно
перед записью, авторизация capability и переходы состояний реализуются на следующих
этапах. `confirmation_epoch` отделён от растущей после ответа ревизии диалога.
Существующий `/reset` очищает только историю; реестр операций и новые таблицы
не удаляются вместе с ней. Команды отзыва карточек будут подключены позже.

## Проверки

```bash
source scripts/env.sh
python -m pip check
python -m ruff check .
python -m ruff format --check .
RUN_INTEGRATION=1 python -m pytest -q
```

Проверяются контракты и схемы SDK, граничные даты и DST, пустые и неизвестные дни,
ошибки файла, передача настроек, состав архива и обновление заполненной БД ЛР1.
Интеграционные тесты используют собственные контейнеры и volumes PostgreSQL.
Настоящие Telegram-, OpenRouter- и погодные запросы для этих проверок не нужны.
Точные результаты финального прогона сохраняются отдельно в
[lab2-stage2-checks.json](evaluation/lab2-stage2-checks.json).

Итог: **355 тестов прошли**, проверки зависимостей и Ruff успешны. Docker-образ
собран и проверен без сети от пользователя UID 10001: SDK импортируется,
шесть миграций и только учебный файл присутствуют, выбор свободного дня и недели
работает. Первые пять SQL-файлов побайтно совпадают с версией `lab1`.
