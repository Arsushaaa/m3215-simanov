## 1. Подготовить запуск

Нужны Python 3.12 из `.venv`, Docker с PostgreSQL, интернет, собственный бот
и локальный `.env` с `BOT_TOKEN` и `OPENROUTER_API_KEY`. Ключи остаются за кадром:
не открывайте `.env`, полный вывод окружения или личную переписку.
Для демонстрации используйте вымышленные учебные данные.

Из корня проекта:

```bash
source scripts/env.sh
bash scripts/docker-local.sh start
bash scripts/start.sh
```

Если среда завершает фоновые процессы, в отдельном терминале выполните
`source scripts/env.sh` и `bash scripts/docker-local.sh run`, оставив его открытым.
В другом терминале проверьте готовность:

```bash
source scripts/env.sh
python -m app.healthcheck
```

Healthcheck проверяет приложение и БД; он не гарантирует успешность следующего
запроса к внешней модели или погодному сервису. Одновременно работает один polling
для одного Telegram-токена. Публичный порт MCP, домен и webhook не требуются:
бот сам запускает локальный дочерний MCP-процесс через `stdio`.

BotFather менять не обязательно. Если нужен актуальный список в меню,
`/setcommands` заменяет его целиком содержимым
[botfather-commands.txt](botfather-commands.txt). Кнопки подтверждения создаёт
приложение; `/setinline` для них не нужен.

## 2. Объяснить устройство за одну минуту

Бот — **MCP-хост**: получает доверенный Telegram update, управляет контекстом,
моделью, правами и ответом. **MCP-клиент** внутри приложения обнаруживает схемы
и вызывает разрешённую возможность. Отдельный **MCP-сервер** публикует
`get_weather`, `get_schedule`, `add_reminder` и ресурс
`schedule://current-week`. Инструмент выполняет действие с аргументами;
ресурс читается по известному URI.

Модель предлагает решение в строгом JSON; приложение проверяет его имя,
аргументы и бюджет. URL, SQL, пути, команды запуска и Telegram-владелец моделью
не задаются. Схемы поступают через MCP discovery. Для чтения результат снова
проверяется и передаётся модели как данные; во втором LLM-запросе инструменты
отключены. После успешной генерации вопрос и итог сохраняются в PostgreSQL,
текст форматируется и отправляется в Telegram.

Проверенная локальная конфигурация — `LLM_TOOL_MODE=native` с бесплатной
`nvidia/nemotron-3.5-super-vl:free`. Модель выбирает функцию, приложение
проверяет единственный вызов и строгий DTO. Нативные схемы содержат вложенные
объекты без `$ref`; JSON-строки вместо этих объектов отклоняются.
Исходный `structured` остаётся программным default. Переключения режима
после ошибки и скрытой перегенерации нет.

Покажите границы в коде: [агент](../app/agent.py),
[MCP-клиент](../app/mcp/client.py), [сервер](../app/mcp/server.py),
[LLM-клиент](../app/llm.py), [подтверждения](../app/confirmations.py) и
[SQL](../app/agent_repository.py). Telegram-обработчик не содержит погодного HTTP,
SQL или собственной копии схем инструментов.

Выбор напоминания и его правки выполняет LLM, включая свободные формулировки.
Покажите «не забудь мне напомнить в 11:00 завтра приготовить пирог», запрос
без точных часов «напомни завтра вечером про пирог» и правку действующей
карточки «нет, лучше на два часа позже». Нужно сверять наблюдаемый результат:
точные параметры либо уточнение, отзыв прежней карточки при правке и отсутствие
записи без кнопки. `reminder_grounding.py` проверяет источники параметров;
семантическую правильность даты проверяет владелец по карточке, а не регулярка.

## 3. Показать независимый MCP-клиент

Эта команда не использует Telegram, модель и погодный HTTP; Docker и ключи
для неё не нужны:

```bash
source scripts/env.sh
python -m scripts.mcp_probe --date 2026-10-13
```

Скрипт запускает настоящий сервер отдельным stdio-процессом через официальный
SDK, выполняет discovery, читает день и недельный ресурс, затем пытается записать
напоминание без полномочий. В JSON покажите:

- ровно три имени: `get_weather`, `get_schedule`, `add_reminder`;
- входные поля, наличие выходных схем и признаки чтения;
- URI `schedule://current-week`, семь дат и зону недели;
- дату `2026-10-13` и статус чтения дня;
- `write_without_context.is_error=true`, код `UNAUTHORIZED`.

Последний отказ происходит до подключения сервера к PostgreSQL. Простого
знания имени инструмента, Telegram ID или UUID действия недостаточно для записи.
Probe автоматически не читает рабочую `.env` бота и не выпускает capability.
Недельный ресурс вычисляется по текущим часам: после срока учебной фикстуры
он честно отмечает отсутствие покрытия, сохраняя семь дат недели.

Разрешённую запись отдельным SDK-клиентом покажите на выделенной тестовой БД:

```bash
RUN_INTEGRATION=1 python -m pytest -q tests/test_integration.py::test_independent_stdio_client_commits_confirmed_reminder_in_real_postgres
```

Тест подготавливает подтверждённое действие и право для синтетического владельца,
проверяет отказ без права, запись с правом и повтор с прежним ID. Он создаёт
собственный контейнер PostgreSQL и не меняет рабочую базу. Capability не нужно
копировать из рабочей БД в Inspector, терминал или отчёт.

## 4. Показать чтение и `/why` в Telegram

В личном демонстрационном чате последовательно:

1. `/start`, `/study`, `/tools`: покажите найденные имена и описания, операции
   чтения и необходимость подтверждения для изменения.
2. «Какая сейчас погода в Санкт-Петербурге, Россия?» Покажите текущие значения,
   время наблюдения и источник. Для одноимённых городов требуется уточнение
   страны или региона; первый результат автоматически не выбирается.
3. `/why`: покажите действие, безопасные аргументы, проверку и результат.
   Это запись приложения из БД; скрытые рассуждения и системные инструкции
   командой не выдаются.
4. «Покажи расписание на 2026-10-13». Явная дата позволяет воспроизвести пример
   независимо от календарной даты защиты.
5. «Есть ли занятия 2026-10-18?» Это известный свободный день учебной фикстуры.
6. «Покажи расписание на 2026-11-01». Отсутствие покрытия не означает свободный
   день: бот должен сообщить об ограничении источника.
7. «Покажи расписание на текущую неделю». Объясните чтение ресурса и текущую
   зону расписания `Europe/Moscow`. За пределами 12–25 октября 2026 года
   нельзя обещать найденные занятия.
8. «Кратко объясни разницу между списком и кортежем в Python», затем `/why`:
   для обычного ответа MCP-вызов не требуется.

Это живые внешние запросы: чтение расходует до двух LLM-обращений,
обычный ответ — до одного. При ограниченной квоте можно сократить живой показ,
остальные случаи предъявив как явно названные автоматические проверки.
Бесплатный endpoint может быть недоступен или вернуть ограничение квоты;
бот сообщает об ошибке и не переходит на платную модель.

## 5. Выбрать зону и подтвердить напоминание

1. `/timezone Россия`: поиск страны выполняется локально. Выберите нужную
   зону, проверьте местное время и нажмите **Использовать этот пояс**.
   Поиск и просмотр сами настройку не меняют. Для городов, например
   `/timezone Санкт-Петербург`, используется фиксированный Open-Meteo geocoding.
2. `/timezone`: покажите сохранённую IANA-зону и текущее время.
   `/timezone Europe/Moscow` — короткий путь явного сохранения для учебного
   примера; укажите фактическую нужную зону при собственном использовании.
3. «Напомни завтра отправить отчёт». Бот должен уточнить точное время,
   не назначая его самостоятельно. Ответьте «в 18:30».
4. Проверьте карточку: текст, точную дату, `18:30`, UTC-offset и IANA-зону.
   Напоминания ещё нет; срок подтверждения — пять минут с подготовки.
5. Напишите «да»: бот направляет к существующей кнопке, без новой карточки,
   LLM-запроса и записи.
6. Нажмите **Подтвердить**. Покажите квитанцию с ID и временем, затем исчезновение
   карточки. `/why` показывает результат подтверждения.
7. Создайте другую учебную карточку и нажмите **Отменить**. Запись напоминания
   не производится; после доставки результата карточка убирается.

При желании покажите отзыв: подготовьте ещё одну карточку, выполните `/stop`
и попробуйте прежнюю кнопку. `/reset`, смена режима, новая карточка и фактическая
смена зоны также отзывают незавершённые действия. `/reset` удаляет историю этого
аккаунта, поэтому используйте демонстрационный чат. Обычный вопрос и поиск зоны
право не отзывают. Уже committed напоминание команды отмены не удаляют.

В ЛР2 напоминание **сохраняется**, уведомление в назначенное время ещё
не отправляется. Планировщик и доставка относятся к ЛР3.

## 6. Объяснить подтверждение, повторы и сбои

Владелец приходит из Telegram update. Карточка хранится в PostgreSQL с точными
параметрами, исходным сообщением, TTL и `confirmation_epoch`. После callback
владельца приложение выпускает 256-битную случайную capability, хранит в БД хеш
и передаёт секрет через доверенную MCP `_meta` отдельно от аргументов модели.
Кнопка содержит ID действия, без capability. Сервер под блокировками сверяет
хеш, владельца, параметры, состояние, срок и epoch. Само наличие `_meta`
права не доказывает.

Транзакции блокируют сначала пользователя, затем действие. Уникальность
по исходному сообщению защищает подготовку; уникальность напоминания по action ID
защищает запись. Ревизия обычного диалога и epoch подтверждения решают разные
задачи. История может очищаться, а реестр операций сохраняет их идентичность.

| Вопрос на защите | Поведение приложения |
|---|---|
| Два нажатия одновременно? | Ограничения и блокировки PostgreSQL дают одну запись; повтор получает прежний ID. |
| БД выполнила commit, но ответ MCP потерялся? | Приложение сверяет то же действие в БД, без автоматического второго MCP-вызова. |
| Проверить исход не удалось? | `OUTCOME_UNKNOWN`, без ложного успеха или заявления об откате; карточка остаётся для проверки прежнего действия. |
| Telegram не доставил квитанцию после commit? | Напоминание сохраняется, карточка остаётся; повтор возвращает прежнюю квитанцию. Строгая однократная доставка Telegram не обещается. |
| Telegram не удалил карточку? | Бот пытается убрать кнопки; запись не откатывается и MCP не вызывается повторно. |
| MCP недоступен? | Обычный диалог доступен, погода и расписание не выдумываются. |
| Источник вернул команду «игнорируй правила»? | Это недоверенные данные. Новые инструменты в финале запрещены; строка не исполняется как код или SQL. |

Повторное нажатие уже удалённой карточки неудобно демонстрировать вручную;
конкурентность, потерю подтверждения commit и ошибки Telegram покажите
контролируемыми тестами:

```bash
RUN_INTEGRATION=1 python -m pytest -q tests/test_integration.py::test_confirmation_services_race_across_pools_commits_once_and_replays_without_mcp tests/test_integration.py::test_reminder_repository_unknown_commit_ack_recovers_same_action
python -m pytest -q tests/test_confirmations.py tests/test_confirmation_handlers.py tests/test_mcp_client.py tests/test_llm_tools.py
```

Telegram, LLM и погодный HTTP здесь подменены; PostgreSQL и отдельные stdio-тесты
настоящие. Полная матрица включает чужого владельца, DST, просрочку, неверные
аргументы, инъекции, отказ внешнего HTTP, перезапуск БД и отмену при завершении
приложения: [28 критериев](evaluation/lab2-stage6-cases.json).

## 7. Показать бюджеты и сохранение ЛР1

| Операция | Максимум LLM | Максимум прикладных MCP |
|---|---:|---:|
| Обычный ответ или уточнение | 1 | 0 |
| Чтение погоды, дня или недели | 2 | 1 |
| Подготовка карточки | 1 | 0 |
| Правка карточки, текстовое согласие или отмена | 1 | 0 |
| Подтверждение кнопкой | 0 | 1 |
| Команды `/tools`, `/why`, `/timezone`; локальные отказы | 0 | 0 |

`tools/call` и `resources/read` делят один бюджет. Discovery происходит отдельно
при запуске. Второй LLM-запрос только составляет итог чтения; повторный выбор
инструмента и бесконечный цикл исключены кодом. Составной запрос нескольких
действий требует выбора одного. Проектный предел одного MCP строже разрешённых
методичкой двух. Стандартные сроки: LLM — 60 с, MCP — 15 с, обработка — 135 с.

В `/translate` покажите короткий перевод; в `/quiz` — тему и первый вопрос.
Сохраняются форматирование, история, настройки и `/stop` из ЛР1.
Готовый длинный текст делится по лимиту Telegram; новая генерация продолжения
требует отдельного сообщения. ЛР1 отдельно зафиксирована тегом `lab1`;
переключать рабочую БД на старый код и откатывать миграции для защиты не требуется.
При отдельном запуске версии ЛР1 используйте собственную БД и окружение
по [инструкции](lab1-defense.md#8-как-показывать-лр1-после-разработки-лр2).

## 8. Предъявить эксперимент и комплект сдачи

Для исторического сравнения показывайте [отчёт](evaluation/lab2-comparison.md)
и предварительную регистрацию `6accc07`: model/T — единственные изменяемые
факторы, dots T=0,3 дала 12/12 и 8/9, дополнительные случаи и MCP-read прошли.
Все 16 отказов Xing сохранены. Старые три прогона ниже объясняйте как разработку
промпта на известном наборе, а не независимое сравнение моделей. Эти результаты
относятся к прежним промптам и схеме. Проверки версии `lab2-final-v2`
предъявляются отдельно по [семантическому сценарию](semantic-routing.md).

Откройте [неизменные 12 запросов](evaluation/lab2-routing.json). Объясните,
что для всех кейсов установлены часы `2026-10-12T09:00:00+03:00`,
зона `Europe/Moscow`, одна модель и одинаковые настройки; предыдущие кейсы
не становятся историей следующего. Ожидаемые решения не отправляются модели.
Для трёх напоминаний оценивается только предложение, без подтверждения и записи.

Предъявите фактические исходные ответы и таблицу «ожидание — действие —
аргументы — результат». Знаменатели фиксированы: `routing_accuracy = верные / 12`,
`argument_accuracy = верные / 9`; пропущенный вызов остаётся ошибкой.
Порог — не менее 10/12 и 8/9. Ошибки анализируются с сохранением первого результата;
после изменения одного элемента повторяются ошибочные кейсы. Подменённая модель
и предыдущие автотесты не доказывают достижение этих порогов настоящей моделью.

Фактические результаты находятся в [анализе эксперимента](evaluation/lab2-experiment.md):
7/12 и 5/9 → 10/12 и 6/9 → 12/12 и 9/9. Менялся только блок правил первого
промпта, повторялся весь набор. Один запрос уточняется локально, поэтому каждый
прогон использовал 11 реальных LLM-вызовов. Для нового эксперимента:

```bash
source scripts/env.sh
python -m scripts.lab2_experiment --env-file .env --output .deploy/evaluation/lab2-repeat.json
```

Новый output расходует бесплатную квоту; существующий checkpoint не повторяет
начатые попытки. Не запускайте генерацию ради простого просмотра уже сохранённых
результатов. [Итоговый отчёт](lab2-report.md) включает архитектуру и применение AI.

Финальная воспроизводимая приёмка, при работающем Docker:
