# ЛР2: команды и подтверждение напоминаний

Этап 5 продолжает существующего Лабби. Новые токены, API-ключи и настройки
BotFather не нужны: используются прежние `BOT_TOKEN` и `OPENROUTER_API_KEY`.
После обновления кода перезапустите приложение обычным способом из
[инструкции окружения](local-environment.md). Подтверждения используют уже готовую
схему `006`: новых миграций и зависимостей на этапе 5 нет. Второй экземпляр polling
с тем же токеном не запускайте.

Из корня проекта, после остановки прежнего процесса бота:

```bash
source scripts/env.sh
bash scripts/docker-local.sh start
bash scripts/start.sh
```

Если среда завершает фоновые процессы, держите `bash scripts/docker-local.sh run`
в отдельном терминале после `source scripts/env.sh`.

## Команды в личном чате

| Команда | Результат |
|---|---|
| `/timezone Europe/Moscow` | Проверяет и сохраняет явно выбранное IANA-имя, показывает текущее время в этой зоне. |
| `/timezone` | Показывает сохранённую зону и время либо просит задать зону. |
| `/tools` | Показывает обнаруженные через MCP имена, описания, чтение или изменение и необходимость подтверждения. |
| `/why` | Показывает безопасную запись о последнем решении только текущего пользователя: время, действие, резюме аргументов, проверку, результат и короткую причину. |

Зону нельзя вывести из языка, города или профиля. Укажите собственную зону:
`Europe/Moscow` — пример, а `+03:00` не заменяет IANA-имя. Для напоминаний,
включая «завтра» и «через два часа», сначала нужна сохранённая зона. Неизвестное
имя не меняет настройку; неоднозначное или несуществующее время при переводе
часов требует уточнения.

Инструменты доступны в `/study`. При отказе MCP `/tools` сообщает об этом;
обычный диалог остаётся доступным. `/why` читает аудит PostgreSQL без вызова
модели: это краткая причина решения, а не скрытые рассуждения, системный prompt
или секреты. Если записей ещё нет, команда сообщает об этом.

## Как сохранить напоминание

1. Выберите `/study` и задайте зону, например `/timezone Europe/Moscow`.
2. Попросите напомнить о событии в будущем, например: «Напомни завтра в 18:30
   отправить отчёт».
3. Проверьте карточку: точный текст, дату, время со смещением UTC и IANA-зону.
   До подтверждения напоминание ещё не сохранено.
4. Нажмите **Подтвердить** или **Отменить**. Подтверждение принимает только
   владелец в своём личном чате, не позднее пяти минут с подготовки карточки.

Пять минут отсчитываются по часам БД и не продлеваются при нажатиях.
Будущее время проверяется повторно перед записью. Изменённые параметры требуют
новой карточки. Успех содержит ID напоминания и точное время с зоной.
Напоминания в ЛР2 **только сохраняются**: отправка уведомлений по времени
относится к ЛР3.

Просьба «напомни завтра приготовить пирог» сначала требует точного времени.
Бот не выбирает 18:00 самостоятельно; часы из прежнего ответа модели не являются
вашим выбором. Можно ответить на уточнение «в 18:30». Если дата или формулировка
не распознаны однозначно, укажите их явно: «Напомни 2026-10-20 в 18:30 приготовить
пирог». Вместо текстового «да» под готовой карточкой нажмите **Подтвердить**:
обычное сообщение разрешения на запись не даёт и карточку не заменяет.

Погода по-прежнему текущая, без прогноза на завтра. Для одноимённых городов
укажите страну, например «Санкт-Петербург, Россия». Пустое название страны
в ответе Open-Meteo заменяется его проверенным ISO-кодом; неоднозначность
сохраняется. Это соответствует [формату Open-Meteo](https://open-meteo.com/en/docs/geocoding-api#json_return_object).

Новая карточка, отмена, `/stop`, `/reset`, смена режима и смена зоны отзывают
ещё не выполненные действия, включая уже принятые к подтверждению. Обычная
переписка не отзывает карточку. Уже сохранённое напоминание эти операции
не удаляют; если отмена совпала с записью, результат определяется транзакцией БД.
Повтор завершённой карточки возвращает прежнюю квитанцию даже после истечения
пяти минут, без новой записи.

Если после MCP-вызова исход записи неизвестен, бот проверяет **то же действие**
в PostgreSQL. Без подтверждённого результата он не сообщает успех и не делает
автоматический повтор MCP. Повторное нажатие той же кнопки сначала проверяет
сохранённый результат; создавать новое напоминание для проверки не требуется.
Сбой отправки сообщения Telegram после commit не откатывает напоминание.

## Меню BotFather — по желанию

Команды, введённые вручную, работают после перезапуска приложения независимо
от меню. Чтобы обновить меню, отправьте BotFather `/setcommands`, выберите
существующего бота и вставьте **весь** файл
[botfather-commands.txt](botfather-commands.txt) одним сообщением.
Список заменяется целиком: только три новые строки уберут прежние команды из меню.
Обновление проекта само не отправляет настройки BotFather или `setMyCommands`.

Кнопки создаёт приложение через `InlineKeyboardMarkup`; включать `/setinline`
не требуется. Токен, ключ OpenRouter, имя, описание и аватар менять не нужно.
Полный профиль и список команд находятся в [botfather.md](botfather.md).

## Как устроено подтверждение

`ConfirmationService` проверяет предложение агента, а `ConfirmationRepository`
одной транзакцией сохраняет действие и пару «вопрос — точная карточка» с проверкой
ревизии диалога. Подготовка уникальна по владельцу и исходному сообщению;
напоминание — по `action_id`. Реестр сообщений хранится отдельно от истории
и переживает `/reset`, поэтому старый update не становится новым действием.

`revision` защищает сохранение ответа от изменений диалога. Отдельный
`confirmation_epoch` определяет действительность карточки и меняется при
её замене или отзыве. Все транзакции записи и отзыва блокируют сначала
пользователя, затем действие. Локальная блокировка asyncio дополняет,
но не заменяет ограничения и блокировки PostgreSQL.

После callback владельца приложение выпускает capability из 256 случайных бит.
`action_id` и capability передаются отдельно от аргументов модели в
`_meta["labbi/action-capability"]`. В PostgreSQL сохраняется только хеш;
сырой секрет остаётся в памяти конкретного вызова и не попадает в callback,
модель, `/why`, журналы или Git. Сервер проверяет хеш, владельца, состояние,
неизменность параметров, срок и epoch под блокировкой перед commit.
Само наличие `_meta` не даёт права записи; независимый клиент без capability
получает отказ.

После перезапуска PostgreSQL сохраняет зону, действие, результат и аудит.
Повторный callback сначала ищет квитанцию. Для того же неотменённого действия
без квитанции допускается ротация capability под блокировкой в пределах
исходных пяти минут: ID, параметры и срок сохраняются, прежнее право отзывается.
Подтверждение не вызывает LLM и выполняет не более одного прикладного MCP-вызова.
Подготовка использует не более одного LLM-запроса и не вызывает `add_reminder`.

## Проверки и воспроизведение

Результаты этапа фиксируются в
[lab2-stage5-checks.json](evaluation/lab2-stage5-checks.json).
Этап завершён 19 октября 2026 года: **767 тестов прошли**, включая 20 интеграционных
с PostgreSQL. Зависимости, Ruff и форматирование проверены. Docker-образ собран
и проверен без сети под UID 10001: настоящий MCP stdio и неопределённый результат
записи при недоступной тестовой БД, без автоматического повтора.
Тесты подменяют Telegram, LLM и погодный HTTP. Интеграционная часть проверяет
настоящие PostgreSQL и MCP stdio; реальные ключи Telegram/OpenRouter не нужны.
Качество маршрутизации настоящей модели проверяется отдельным экспериментом
этапа 7; этот прогон проверяет код и границы компонентов.

Проверки без Docker и тесты без маркера `integration`:

```bash
source scripts/env.sh
python -m pip check
python -m ruff check .
python -m ruff format --check .
python -m pytest -q -m "not integration"
```

Полный прогон, включая PostgreSQL, после запуска Docker:

```bash
source scripts/env.sh
bash scripts/docker-local.sh start
RUN_INTEGRATION=1 python -m pytest -q
```

Контракты, ограничения и критерии приёмки описаны в [spec.md](../spec.md),
фактический прогресс и следующие этапы — в [plan.md](../plan.md).
