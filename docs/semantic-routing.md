## Маршрутизация

Промпт — `app/agent_prompts.py`. Просьба «не забудь мне напомнить в 11:00 завтра
приготовить пирог» передаётся модели целиком, без разрешения по ключевым словам.
Даты вычисляются из доверенных часов и сохранённой IANA-зоны. Отрицание,
цитату, перевод и неизвестное время различает модель. Несколько действий
требуют выбора одного, без частичного исполнения.

Для погоды модель переводит `Kazan, Russia` в `Казань, Россия`; неизвестную
страну не добавляет. MCP принимает только русское имя, геокодер получает
`language=ru`. Перевод не устраняет одноимённые места: нужен выбор страны/региона.
Подробности — [погодный контракт](weather.md).

| Действие | Максимум LLM | Максимум прикладных MCP |
|---|---:|---:|
| Обычный ответ или уточнение | 1 | 0 |
| Погода, день или неделя расписания | 2 | 1 |
| Подготовка, правка или уточнение напоминания | 1 | 0 |
| Текстовое согласие или отмена карточки | 1 | 0 |
| Подтверждение кнопкой | 0 | 1 |

Второй LLM-запрос после чтения только составляет итог; инструменты отключены.
Нативный `prepare_reminder` — адаптер подготовки приложения. Настоящий MCP
`add_reminder` доступен только подтверждённой кнопке владельца с capability.
Автоматических повторов и продолжения генерации нет.

## Программные проверки

Для предложения модель возвращает параметры и `evidence`: дословные цитаты
пользовательских сообщений с индексами. Индекс 0 — текущая реплика; предыдущие
получают индексы в контексте. Ответ ассистента не является допустимым источником.
Сохраняемые поля действующей карточки обозначаются ссылкой `pending_card`;
их значения берутся из PostgreSQL, не из свободного текста модели.

`app/reminder_grounding.py` проверяет существование цитат и неизменность
унаследованных полей. Это проверка происхождения, не доказательство правильного
понимания языка. Смысл даты/часов извлекает модель; пользователь проверяет
точные параметры в карточке. Программа независимо проверяет типы, календарь,
будущее время, offset, IANA и DST. Не-UTC локальный момент проверяется до
преобразования, чтобы не маскировать несуществующее время при переходе часов.

В коде остаются технические проверки формата и локальный отказ от чрезмерного
вывода. Они не выбирают MCP и не интерпретируют напоминания. В `/translate`
и `/quiz` инструменты по-прежнему недоступны.

## Конкурентные подтверждения

До LLM PostgreSQL атомарно захватывает запрос и сохраняет снимок карточки/epoch.
Дубликат update не получает второй захват. Пока новый текст обрабатывается,
старая кнопка и ранее выданная capability не могут записать прежнее действие:
проверка выполняется при подтверждении и внутри MCP-сервера.

Семантическая правка отзывает прежнее действие до завершения аудита. Новая
карточка сверяет epoch под блокировкой владельца. `/stop`, сброс, смена
режима/зоны и новая карточка не позволяют воскресить старое решение.
Успешный несвязанный вопрос сохраняет карточку. Если разобрать новый текст
не удалось, неподтверждённая карточка отзывается безопасным отказом.
Квитанции уже выполненных действий доступны. Миграции `001`–`006` не менялись;
рассылки напоминаний ещё нет.

## Ограниченный реальный прогон

[Замороженный протокол](evaluation/semantic-routing-smoke-20261026/manifest.json)
содержит шесть случаев: исходную просьбу о пироге, отрицание, английское имя
города, неизвестные часы, переставленную формулировку и относительную правку
реальной по структуре карточки. Температура 0,2, часы 26 октября 2026, 10:00
в Europe/Moscow. Источники, план, каталог и параметры сверяются по hash.
Ожидания не передаются модели. Протокол коммитится до API.

`scripts/semantic_routing_smoke.py` допускает максимум один LLM на случай,
всего шесть. Места попыток сохраняются до отправки; прерванные и ошибочные
не повторяются. Погодный выбор останавливается перед MCP-исполнением, карточки
и история изолированы в памяти, SQL и Telegram не используются. Это проверка
конкретного изменения, не независимая оценка общей точности маршрутизации.
Она не заменяет PostgreSQL/MCP-проверки записи и подтверждения.

```bash
python -m scripts.semantic_routing_smoke --env-file .env \
  --folder docs/evaluation/semantic-routing-smoke-20261026 --run
```

Повтор этой команды не повторяет уже начатые попытки. Для нового прогона нужен
отдельный протокол, текущие manifest/results сохраняются.

Первый [реальный результат](evaluation/semantic-routing-smoke-20261026/results.json)
не прошёл: 2/6 действий, 0/4 аргументов. Модель вычисляла дату/часы, но просила
лишнее подтверждение до подготовки карточки; погодный случай завершился
тайм-аутом. Все шесть попыток сохранены, ошибка не исключена из знаменателя.

После этого промпт явно требует сразу подготовить карточку при вычислимых
параметрах и не заменять её повторным вопросом о времени. Подтверждение остаётся
кнопкой. Параллельный review добавил отказ от неполных управляющих DTO и запрет
публикации более старой карточки при уже зарегистрированном новом запросе.
Дополнительные проверки покрывают обе гонки и повтор прежней карточки.

Второй [протокол](evaluation/semantic-routing-smoke-20261026-v2/manifest.json)
содержит те же шесть входов и те же ожидания; изменены исходники и промпт,
новая версия также коммитится до API. Это проверка исправления на известном
наборе, а не независимый сравнительный эксперимент.

Второй [результат](evaluation/semantic-routing-smoke-20261026-v2/results.json)
тоже не прошёл: 2/6 действий, 0/4 аргументов. Вычисленные моменты уже были
корректны, но модель ссылалась на отсутствующую карточку либо называла
изменённое время унаследованным. Проверка источников отвергала эти предложения.
Погодный случай вновь завершился тайм-аутом. Эти ошибки сохранены полностью.

В третьей версии модельная схема при отсутствии карточки разрешает только
пользовательские источники. Для изменённого времени явно требуется цитата
новой просьбы. Подсказки JSON-схемы для провайдера не содержат regex-pattern;
канонические Pydantic/MCP-проверки русского входа остаются обязательными.
Схема строится из контракта, она не распознаёт намерение или конкретную фразу.
Третий [протокол](evaluation/semantic-routing-smoke-20261026-v3/manifest.json)
сохраняет те же входы и ожидания; это ещё один открыто зафиксированный этап
проверки исправления, без перезаписи первых результатов.

Третий [результат](evaluation/semantic-routing-smoke-20261026-v3/results.json):
3/6 действий, 2/4 аргументов. Исходная и переставленная просьбы дали правильные
карточки на 11:00, но модель не перевела city, придумала часы для «вечером»
и лишний раз уточнила относительную правку. Эти нарушения также сохранены.

Четвёртый промпт формулирует правила маршрутизации на английском, выделяет
приоритет проверки точности времени и помещает авторитетный снимок состояния
в конец системного контекста. Русский язык ответа и дословные исходные цитаты
сохраняются. Четвёртый [протокол](evaluation/semantic-routing-smoke-20261026-v4/manifest.json)
снова использует те же входы и ожидания; результаты предыдущих этапов не изменяются.

Четвёртый [результат](evaluation/semantic-routing-smoke-20261026-v4/results.json)
не прошёл: 2/6 действий, 1/4 аргументов. Перевод города сработал, однако dots
путала личное напоминание с чтением учебного расписания. После уточнения
назначения инструментов зарегистрирован тот же набор для бесплатной
`nvidia/nemotron-3.5-super-vl:free`:
[протокол](evaluation/semantic-routing-smoke-20261026-nvidia35/manifest.json).
Это отдельная проверка пригодности endpoint, не автоматический fallback.

Параметр `--max-new-cases 1` позволяет проверить первую ещё не начатую попытку
и затем продолжить остальные. Он не меняет порядок, лимит шести вызовов,
ожидания или знаменатели 6/4: неполный прогон не считается прошедшим.


### Упорядочение схемы декодера

Первая попытка бесплатной `nvidia/nemotron-3.5-super-vl:free` также не прошла:
модель выбрала погоду, хотя в reason назвала запрос напоминанием. Сохранена
единственная попытка, остальные пять не запускались. Это не успешный результат
и не основание переключать рабочий `.env`.

При анализе схемы обнаружено различие порядка полей: ReminderDecision наследовал
arguments/evidence до action/name, а у погоды/расписания action/name шли первыми.
Декодер с фиксированным порядком ключей мог исключать ветку напоминания после
начала ответа с action. Дополнительно вложенный Pydantic discriminator содержал
объект вместо обычной ссылки в mapping. Это гипотеза причины, не доказательство.
ReminderDecision теперь явно задаёт action/name первыми; проекция для провайдера
разворачивает вложенный oneOf и удаляет discriminator. Каноническая строгая
Pydantic/MCP-валидация сохраняется. Новый опыт использует прежнюю dots и те же
шесть формулировок: [манифест](evaluation/semantic-routing-smoke-20261026-flat/manifest.json).

Причина decoder не доказана; пять остальных попыток не запускались.
