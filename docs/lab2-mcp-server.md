# ЛР2, этап 3: собственный MCP-сервер

Сервер работает отдельным процессом через `stdio`: стандартный ввод и вывод
заняты MCP, диагностические сообщения идут в `stderr`. Публичный порт не нужен.
Сервер предоставляет три инструмента и один ресурс. Подключение к Telegram и
выбор действия моделью относятся к следующим этапам.

Этап завершён 18 октября 2026 года. Полный прогон: **490 тестов прошли**,
включая конкурентные транзакции PostgreSQL и настоящий MCP stdio. Docker-образ
собран; сервер проверен в контейнере без сети под пользователем 10001.
Сохранены [результат независимого клиента](evaluation/lab2-stage3-probe.json)
и [протокол проверок](evaluation/lab2-stage3-checks.json). Погодный HTTP в тестах
подменён; реальные Telegram, OpenRouter и Open-Meteo не вызывались.

## Независимая проверка без внешних API

Из корня проекта, в подготовленном окружении:

```bash
source scripts/env.sh
python -m scripts.mcp_probe
```

Это отдельный MCP-клиент из официального SDK. Он запускает настоящий дочерний
процесс `python -m app.mcp.server`, получает инструменты и схемы через discovery,
читает расписание и недельный ресурс. Затем проверяет, что `add_reminder` без
доверенного контекста получает `UNAUTHORIZED` **до подключения к PostgreSQL**.
Погода, Telegram и OpenRouter этой проверкой не вызываются; напоминание не создаётся.

Проверка выводит JSON с именами инструментов, полями входа, наличием выходных
схем, признаками чтения, URI ресурса, датами недели и кодом отказа записи.
Секреты, названия занятий и аудитории в этот отчёт не попадают.
Ожидаемый фрагмент:

```json
{
  "transport": "stdio",
  "resources": ["schedule://current-week"],
  "write_without_context": {
    "is_error": true,
    "code": "UNAUTHORIZED"
  }
}
```

Для выбранной даты учебного расписания:

```bash
python -m scripts.mcp_probe --date 2026-10-13
```

Фикстура покрывает 12–25 октября 2026 года. После этого периода ресурс всё равно
возвращает семь дат текущей недели, но честно отмечает дни вне покрытия.
Это не означает отсутствие занятий.

## Настройки и самостоятельный запуск

Сервер и проверочный клиент автоматически не читают рабочую `.env` бота.
Необязательный `--env-file` задаёт отдельный файл серверных настроек:

```bash
python -m scripts.mcp_probe --env-file .tools/mcp-test.env
python -m app.mcp.server --env-file .tools/mcp-test.env
```

Вторая команда ожидает MCP-сообщения на стандартном вводе; обычный текст в этом
терминале не является запросом к серверу. Для удобной проверки используйте клиент.

Сервер читает только настройки PostgreSQL, расписания и тайм-аута MCP.
Проверочный клиент передаёт дочернему процессу этот ограниченный набор;
токен Telegram и ключ OpenRouter ему не нужны. Сервер не применяет миграции сам:
схему подготавливает существующий механизм запуска приложения или тестовая фикстура.
Для discovery и расписания PostgreSQL не требуется. Подключение к БД создаётся
при допустимом вызове записи и закрывается при завершении процесса.

Личный локальный файл подключается через `SCHEDULE_FILE`, а его зона должна
совпадать с `SCHEDULE_TIMEZONE`. Не добавляйте личные файлы в Git. При формировании
ответов Telegram-агентом на следующих этапах найденные занятия будут передаваться
модели; независимая проверка из этой инструкции модель не использует.
Автоматическая облачная упаковка включает только учебный `data/schedule.json`.

## Обнаруживаемые контракты

| Возможность | Вход | Результат |
|---|---|---|
| `get_weather` | `city` | Наблюдение, отсутствие города, варианты уточнения или безопасная ошибка |
| `get_schedule` | `date` в формате `YYYY-MM-DD` | Занятия, известный свободный день, отсутствие покрытия или ошибка |
| `add_reminder` | `text`, `remind_at` с UTC-offset | Квитанция созданного/ранее созданного напоминания или отказ |
| `schedule://current-week` | URI ресурса | JSON семи дат от понедельника до воскресенья в зоне расписания |

Входные и выходные схемы инструментов публикуются сервером через MCP.
Результаты инструментов находятся в `structuredContent`; текстовый JSON-блок
дублирует их для совместимости. Ошибки выполнения имеют `isError=true` и
безопасный код. JSON ресурса передаётся как `TextResourceContents` с MIME
`application/json`, а не как результат инструмента.
Неизвестный URI ресурса получает протокольную ошибку «Ресурс не найден»,
произвольные локальные пути через MCP не читаются.

Аргументы, выходные данные и размер результата проверяются сервером.
Результат ограничен 32 КиБ; ожидание MCP имеет конечный тайм-аут.
Погодный адаптер обращается только к фиксированным адресам Open-Meteo.
Если найдены несколько подходящих городов, первый автоматически не выбирается.
Текст источника остаётся данными и не исполняется как инструкция, SQL или команда ОС.

## Почему независимый клиент не может создать напоминание

Идентификатора пользователя в модельных аргументах нет. Для записи требуется
ранее подготовленное и подтверждённое действие в PostgreSQL, связанное с владельцем,
неизменными параметрами, `confirmation_epoch` и общим сроком до пяти минут.
Приложение передаёт отдельное непредсказуемое право в прикладном MCP `_meta`.
Наличие самой `_meta`, знание Telegram ID или UUID действия полномочий не дают.
Сервер сверяет право и состояние под блокировками в транзакции записи.

Проверочный клиент намеренно не выпускает таких прав. Для проверки разрешённой
записи используются отдельная тестовая PostgreSQL и тестовая идентичность,
подготовленные интеграционными фикстурами. Рабочую базу для такой демонстрации
использовать не следует. Будущие Telegram-кнопки подтверждения появятся на этапе 5.

Повтор завершённого действия возвращает прежнюю квитанцию без второго напоминания.
Ошибка доставки ответа не откатывает выполненную запись. При неопределённом исходе
нельзя утверждать успех или создавать действие с новым ключом: проверяется прежнее
действие. Отправка уведомления в назначенное время относится к ЛР3.

## Автоматические проверки

```bash
python -m pytest -q tests/test_mcp_server.py
RUN_INTEGRATION=1 python -m pytest -q -m integration
```

Протокольные тесты используют настоящий SDK-клиент, сервер в памяти и отдельный
stdio-процесс. Telegram, модель, погодный HTTP и БД в этой группе не вызываются.
Проверяются discovery, схемы, точные поля результата, неверные аргументы и имя,
тайм-аут, неправильный/слишком большой результат и передача права вне аргументов.
Проверки действительных транзакций PostgreSQL запускаются отдельно и требуют Docker.
Сценарий `test_independent_stdio_client_commits_confirmed_reminder_in_real_postgres`
запускает независимый stdio-процесс с отдельной тестовой PostgreSQL: сначала
проверяет отказ без права, затем разрешённую запись и повтор с тем же ID.
После закрытия клиента проверяет освобождение серверных соединений БД.
