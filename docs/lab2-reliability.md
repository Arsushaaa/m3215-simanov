# ЛР2: надёжность и отказы — этап 6

Приёмка связывает требования с конкретными тестами, их фактическими результатами
и явным безопасным исходом. Качество выбора инструмента настоящей моделью
проверяется отдельно на этапе 7; здесь Telegram, LLM и погодный HTTP подменены.
PostgreSQL, его перезапуск и MCP stdio проверяются настоящими процессами.

## Воспроизведение

```bash
source scripts/env.sh
bash scripts/docker-local.sh start
python -m scripts.lab2_reliability
```

Если среда завершает фоновые процессы Docker, используйте отдельный терминал
с `source scripts/env.sh` и `bash scripts/docker-local.sh run`.
Реальные ключи Telegram/OpenRouter и пользовательская БД не используются:
интеграционные тесты создают и удаляют собственные контейнеры `itmo-test-*`.

Команда проверяет зависимости, Ruff, форматирование и полный pytest с
`RUN_INTEGRATION=1`. JUnit сохраняется временно; отчёт содержит только результаты,
имена тестов и статусы, без payload/traceback. `PYTEST_ADDOPTS` и внешние плагины
из переменных окружения не могут незаметно превратить этот запуск в частичный.
Для проверки базовых версий нужна полная Git-история; CI получает её через
`fetch-depth: 0`.

Источники результатов:

- [28 критериев и ожидаемые исходы](evaluation/lab2-stage6-cases.json).
- [Фактический протокол](evaluation/lab2-stage6-checks.json): команды, исходы
  каждого критерия, количество прошедших/упавших/пропущенных тестов.
- [Сборка и проверка контейнера](evaluation/lab2-stage6-container.json).

Критерий считается пройденным, только если все указанные тесты найдены в JUnit
и каждая собранная параметризация прошла. Пропуск, отсутствие теста или ошибка
дают неуспешную приёмку. Дополнительно проверяются Python 3.12, неизменность
миграций `001`–`006`, тег `lab1` и исходные 12 запросов эксперимента. Базовые
данные читаются из фиксированных Git-коммитов, а не из редактируемого отчёта.

## Исправленные проблемы

| Ситуация | Прежнее поведение | Проверенное поведение |
|---|---|---|
| MCP вернул расписание с правильной схемой, но на другую дату | Данные могли попасть в итог модели | `INVALID_RESULT` до итогового LLM |
| Квитанция MCP относится к другому моменту напоминания | Одной схемы было недостаточно | `OUTCOME_UNKNOWN`; сверяется тот же action в БД, без повторного MCP |
| Приложение останавливается во время `/why` или отзыва перед `/reset` | Задача могла пережить закрытие пула/Telegram-сессии | Router отменяет и дожидается генераций, callbacks, команд и отзыва |
| Один ресурс выдаёт ошибку при `close` | Последующие ресурсы могли остаться открытыми | Все остальные закрываются; каждый close ограничен 10 секундами; неисправный пул принудительно завершается |
| Повторная отмена приходит во время cleanup | Cleanup мог прерваться | Закрытие защищено и дожидается завершения; затем отмена передаётся вызывающему коду |
| SDK логирует Telegram update или тело исключения | В журнал могли попасть ID, username и текст | Сохраняются категория, уровень и класс ошибки; payload и traceback исключены |

Диагностика приложения сохраняет фиксированные сообщения, технические статусы
и случайные request ID. Ключи и пароли дополнительно скрываются `SecretFilter`.
Краткий аудит решений остаётся в PostgreSQL и доступен владельцу через `/why`.

## Проверки PostgreSQL

В [интеграционных тестах](../tests/test_integration.py) проверены:

- Восемь подготовок одного пользовательского сообщения создают одно действие,
  одну пару истории, один реестр запроса и исходный срок подтверждения.
- Шесть одновременных подтверждений через два независимых пула создают одно
  напоминание. Повтор после commit возвращает прежний ID без нового MCP-вызова.
- Отказ аудита откатывает выдачу права и отзыв для `pending` и `approved`:
  `approve`, отмена, `/stop`, `/reset`, смена режима и зоны — 12 сочетаний.
  Действие, capability hash, epoch, история, реестр и аудит не меняются частично.
- Настоящий stop/start PostgreSQL и новые пулы сохраняют зоны, историю,
  pending/approved/committed, квитанции и безопасный аудит. Право approved
  восстанавливается для того же действия; чужой владелец не получает данных.
- Потеря ответа после commit восстанавливает квитанцию того же action.
  Отсутствие подтверждённого commit остаётся неизвестным исходом.

Подготовка и запись защищаются уникальностью и блокировками БД. Локальный
`asyncio.Lock` упорядочивает интерфейс одного процесса, но не заменяет эту защиту.

## Границы результата

Чтение использует максимум 2 LLM/1 MCP, обычный ответ — 1 LLM/0 MCP,
подготовка — не более 1 LLM/0 MCP, callback — 0 LLM/не более 1 MCP.
Отказ или разрыв MCP сохраняет обычный диалог; погода и расписание требуют
проверенного результата. Второе LLM-обращение не может запустить новый инструмент.
В тестах инъекции это проверяется для structured и native HTTP-ответов.

Квитанция отправляется до удаления карточки. Ошибка доставки не откатывает
commit и сохраняет карточку для проверки прежнего действия; неизвестный исход
не объявляется успехом. Повторная доставка квитанции возможна. При ошибке
удаления приложение пытается убрать кнопки, не повторяя запись.

Подмена модели проверяет границы приложения, а не качество реальной генерации.
