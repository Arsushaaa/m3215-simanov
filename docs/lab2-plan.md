# Лабораторная № 2: согласованный обзор

17 октября 2026 года пользователь одобрил начало первого этапа и ограничение
агентного сценария. Канонические документы: [спецификация](../spec.md),
[план с прогрессом и проверками](../plan.md), [правила разработки](../AGENTS.md).
Этот файл остаётся кратким обзором; детальные контракты и статусы находятся там.

ЛР1 сохранена аннотированным тегом `lab1` на коммите `2d10cf0`: отчёт,
эксперимент и 230 успешных тестов входят в эту версию. Тег не перемещается.
Первый этап ЛР2 меняет только документы; MCP, новые команды, зависимости
и миграции пока не реализованы.

## Результат для пользователя

| Запрос | Возможность |
|---|---|
| «Какая сейчас погода в Казани?» | `get_weather(city)` получает текущие данные погодного сервиса |
| «Какие занятия завтра?» | `get_schedule(date)` читает обезличенный JSON-файл |
| «Покажи текущую неделю» | Ресурс `schedule://current-week`, только чтение |
| «Напомни завтра в 18:30 отправить отчёт» | `add_reminder(text, remind_at)` сохраняет запись после подтверждения |

Напоминания в ЛР2 **только сохраняются**. Отправка уведомлений по времени
относится к ЛР3. Часовой пояс пользователь задаёт через `/timezone`,
а `/tools` показывает обнаруженные действия и `/why` — безопасное объяснение
последнего решения.

## Принятые ограничения

- MCP работает локально через `stdio`: бот запускает дочерний процесс.
  Публичный порт или отдельная облачная машина не нужны.
- Инструменты доступны в `/study`; `/translate` и `/quiz` сохраняют назначение.
- Обычный ответ, уточнение и подготовка напоминания: максимум один LLM-запрос,
  без прикладного MCP-вызова.
- Чтение данных: максимум два LLM-запроса и один MCP-вызов. Во втором LLM-запросе
  инструменты отключены; он только формирует ответ по проверенным данным.
- Подтверждение кнопкой: ноль LLM-запросов, не более одного MCP-вызова.
  Подготовленные параметры показываются до записи, подтверждение живёт до пяти минут.
- `tools/call` и `resources/read` используют общий лимит одного прикладного
  вызова; discovery при подключении учитывается отдельно. Составной запрос,
  требующий нескольких действий, сначала уточняется. Автоматических цепочек
  генерации и повторов LLM/MCP нет; `/stop` сохраняется.
- Владелец приходит из доверенного Telegram update, вне аргументов модели.
  Сервер проверяет отдельное право на подтверждённое действие. Повторы и гонки
  защищаются транзакциями и уникальностью PostgreSQL.
- Модель остаётся бесплатной `nvidia/nemotron-3-super-120b-a12b:free`,
  платных запасных моделей нет. Перед подключением проверяются поддержка
  tool calling и совместимость официального Python MCP SDK.

Эти решения выбраны для нашего проекта. Методичка допускает до двух
MCP-вызовов на сообщение; согласованный проектный предел строже.
Инструментальное чтение расходует до двух обращений из общей квоты OpenRouter.

## Этапы

1. Спецификация, план и правила проекта — текущий этап.
2. Зависимости, данные, контракты и новые миграции.
3. MCP-сервер и проверка независимым клиентом.
4. MCP-клиент и ограниченный агентный сценарий.
5. Подтверждения и новые Telegram-команды.
6. Конкурентные повторы, ошибки, безопасность и совместимость ЛР1.
7. Эксперимент, отчёт, инструкция и тег `lab2`.

Каждый завершённый этап сохраняется отдельным коммитом. Полные критерии
и границы каждого этапа приведены в [plan.md](../plan.md).

Эксперимент использует неизменные [12 базовых запросов](evaluation/lab2-routing.json)
и зафиксированное там время `2026-10-12T09:00:00+03:00`, а не часы компьютера.
Требуются минимум 10/12 правильных действий и 8/9 корректных аргументов.
