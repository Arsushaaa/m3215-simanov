# ЛР3, этап 4: город, согласие и исходящая очередь

Добавлены настройки и хранилище заданий. **Worker, отправка по времени и ежедневная
генерация сводки ещё не запускаются**: это этапы 5 и 6. `/notifications` и включение
подписки прямо сообщают, что служба доставки пока не подключена.

| Команда | Действие |
|---|---|
| `/city <название>` | Поиск, выбор места, просмотр координат и отдельное подтверждение |
| `/city` | Текущий город и подсказка по вводу |
| `/briefing_on` | Явное согласие на будущую сводку при наличии зоны, города и личного чата |
| `/briefing_off` | Отзыв согласия и отмена ещё не начатых заданий сводки |
| `/notifications` | Город, пользовательский пояс, согласие, регистрация чата и плановое время |

Команды работают сразу после обновления приложения. Изменение `/setcommands` в
BotFather нужно только для меню; готовый список находится в botfather-commands.txt.

`/city Москва` и `/city Paris, France` обращаются к фиксированному Open-Meteo
Geocoding API, переиспользуют проверку одноимённых мест погодного адаптера и
локальные названия стран CLDR из меню часовых поясов. LLM не вызывается.
Нет фильтра населения и выбора «самого популярного» города. Сохраняются отдельные
GeoNames ID; если подписи совпадают, пользователь видит координаты и зону.
Поиск ограничен: API запрашивает до 100 мест, меню содержит до 50 по шесть на странице.
Сначала место выбирается, затем показываются название/страна/регион, точные
координаты и зона. Только кнопка «Сохранить город» меняет профиль.

Меню хранится в PostgreSQL, а не только в памяти процесса. У него владелец,
случайный токен 128 бит (в БД только SHA256), TTL пять минут от начала поиска,
версия профиля и выбранный индекс. Кнопки не содержат координаты, actor или адрес.
Изменение зоны/согласия/города, новый поиск, отмена, `/stop`, сброс и смена режима
делают старый выбор недействительным. Отложенный ответ геокодера не восстанавливает
удалённое меню. Подтверждение и отмена линеаризуются блокировкой menu под блокировкой
владельца; чужая кнопка и просрочка не сохраняют место. Соединение БД не удерживается
во время HTTP. После сохранения/отмены UI удаляет прежнюю карточку тем же механизмом,
который использовался для выбора часового пояса. Сам подтверждённый город не удаляется
при обычном сбросе истории. Зона города не подменяет пользовательский `/timezone`.

Адрес доставки хранится в `labbi_notification_profiles.destination_chat_id` отдельно
от владельца. Handler передаёт actor из from_user и chat из реального private update;
регистрация проверяет их соответствие. Поле не заполняется из текста, модели, MCP
или автоматически из старого user_id. По умолчанию подписка false. Для legacy
нужен новый update, например `/start`. Статус не показывает внутренние IDs.

Сводка требует подтверждённого города, пользовательской IANA-зоны и адреса.
`/briefing_on` сохраняет время согласия и показывает ближайшие будущие 08:00
по локальному календарю; точно в 08:00 выбирается следующий день. Нет рассылки
за время до согласия. Повторное включение не сбрасывает время согласия/версию.
Переходы DST считаются через IANA, а не прибавлением 24 часов к UTC; невозможное
или неоднозначное время не заменяется произвольным часом.

Новый `008_notifications.sql` добавляет profile, city_menus и outbox. Старые
001–007 не изменены. SQL-триггер вставляет событие напоминания в той же транзакции,
где сохраняется подтверждённое напоминание. Если запись outbox не удалась, само
напоминание и смена состояния действия откатываются. При повторе action возвращает
прежнюю квитанцию; уникальный reminder_id защищает событие от дубля. Если адреса
ещё нет, исходящая запись не получает выдуманный адрес. После нового private update
подбираются лишь будущие/ещё актуальные напоминания с окном опоздания до 15 минут.

Задание сводки имеет UNIQUE(user_id, local_date), согласие и expected_profile_version.
Repository принимает только текущий/следующий локальный день, время после согласия
и ещё не истёкшее окно. Повторные и конкурентные подготовки возвращают один UUID.
Подготовленный payload пока не генерируется; API очереди проверен интеграционно.
Планировщик, который будет вызывать его в нужное время, появится на этапе 6.

Состояния outbox: pending, preparing, ready, sending, retry_wait, sent, failed,
missed, cancelled. Хранятся due/deadline, адрес/зона/версия, payload, attempts<=3,
next_attempt_at, lease/token/version и слоты бюджета LLM<=1/MCP<=3 для будущей сводки.
CHECK запрещают несовместимый lease, отправку без payload, лишние попытки и неверный
deadline. Смена профиля или зоны увеличивает version, отменяет pending/preparing/
ready/retry_wait сводки и очищает их lease. sending остаётся sending: HTTP мог уже
начаться. Зарезервированные LLM/MCP-слоты не обнуляются. Безопасно переоткрывается
только отменённое будущее событие без payload, попыток и потраченного бюджета;
уже начатую подготовку этой даты новая версия не генерирует заново. Напоминания
остаются отдельными заданиями и не удаляются вместе с подпиской на сводку.
UNIQUE обеспечивает одну внутреннюю запись, а не строго одну внешнюю доставку.

Для будущей фоновой погоды MCP get_weather расширен точечной веткой:
`{"point":{"latitude":55.79,"longitude":49.12,"timezone":"Europe/Moscow"}}`.
Это публичные координаты, без владельца, адреса и подставленной подписи места.
Ответ повторяет точку, содержит наблюдение/зону и проверяется клиентом на точное
соответствие запросу. Геокодирование не выполняется. Обычная модель видит только
старый `{"city":"Казань"}`; Scope без host-флага allow_point отвергает точку до MCP.
Флаг разрешён только для Lifestyle, а будущая сводка сформирует точку из профиля.
Независимый SDK-клиент может читать произвольные публичные координаты, но не чужой
профиль по ID. Полная прежняя city-wire-схема сервера поддерживается отдельно и
point не разрешает; произвольные изменения discovery по-прежнему отвергаются.
