# Поиск города и ошибки погодного сервиса

В режиме `/study` инструмент `get_weather` получает текущие наблюдения
Open-Meteo. Сначала выполняется геокодирование, затем — запрос погоды только
для однозначно найденного места. Страна и регион передаются через запятые:
`Казань, Россия, Татарстан`. Минимального населения и выбора крупнейшего города нет.
Короткое название также сохраняет полные названия с теми же начальными словами:
`Ростов` включает `Ростов-на-Дону` и `Ростов Великий`, но не `Ростовка`.

## Исправление неоднозначности — 19 октября 2026 года

Реальный публичный ответ геокодера на `Казань` сохранён в
[`open_meteo_kazan.json`](../tests/fixtures/open_meteo_kazan.json). В нём есть
Казань в Татарстане и три населённых пункта в Кировской области с разными
GeoNames ID и координатами, но одинаковыми доступными подписями. Прежде эти
повторы превращали весь поиск в `INVALID_ARGUMENTS`; клиент показывал сообщение
«Аргументы инструмента не соответствуют допустимому формату».

После этого исправления для выбора показываются уникальные подписи, а исходные места
сохраняются раздельно. `Казань` давала уточнение с вариантами в Татарстане и Кировской области.
`Казань, Татарстан` однозначно определяет координаты и разрешает запрос погоды.
`Казань, Кировская область` обозначала три места: бот выдавал
`AMBIGUOUS_PLACE` с понятным сообщением о недостаточной точности геокодера.
Превращать этот вариант в одну локацию или брать первый ID запрещено.

## Полные названия и проверка скриншотов — 25 октября 2026 года

Повторная проверка публичного источника выявила отдельную ошибку короткого названия.
В ответе на `Ростов` единственное точное совпадение — населённый пункт в Украине;
`Ростов-на-Дону` и `Ростов Великий` тоже присутствуют, но прежний exact-name фильтр
их отбрасывал. Это ошибочно превращало неоднозначный запрос в погоду для одной точки.
Полный ответ сохранён в
[`open_meteo_rostov.json`](../tests/fixtures/open_meteo_rostov.json).

Теперь сохраняются точные названия и полные названия, продолжающие введённые слова
через пробел или дефис. `Ростов` предлагает три варианта, `Ростов, Россия` — два
российских города, `Ростов-на-Дону` или `Ростов, Ростовская область` однозначно
выбирают город на Дону. `Ростово`, `Ростовка` и другие продолжения внутри слова
не подменяют исходное название. Население, порядок ответа, язык сообщения и
часовой пояс пользователя не считаются подтверждением страны или города.
Это общее правило сопоставления слов, без особого исключения для Ростова.

По тому же правилу реальный ответ на `Казань` теперь также сохраняет `Казань-Омга`.
`Казань, Кировская область` предлагает подписи `Казань` и `Казань-Омга`; группа
нескольких ID с подписью `Казань` остаётся несколькими точками. Если в найденном
наборе осталась только неразличимая группа, возвращается `AMBIGUOUS_PLACE`.

Публичный ответ на `Москва` сохранён в
[`open_meteo_moscow.json`](../tests/fixtures/open_meteo_moscow.json). Текущий код
обрабатывает повторяющиеся подписи без `INVALID_ARGUMENTS`, предлагает до пяти
различимых вариантов и не отсекает деревню с 17 жителями в Тверской области.
Одной страны `Россия` поэтому недостаточно; `Москва, Россия, Москва` выбирает
столицу по проверенному административному названию, а не по её известности.
Если при этих запросах появляется прежняя ошибка аргументов, нужно проверить,
что запущен код после исправления 19 октября, включая собранный Docker-образ.

Для `Санкт-Петербург` источник действительно возвращает два разных GeoNames ID:
город в России и место в Монтсеррате (`MS`). Запись `MS` не выдумана моделью.
Поскольку пользователь не указал страну, бот уточняет её; ответ
`Санкт-Петербург, Россия` выбирает российские координаты. Другую запись нельзя
скрывать только из-за неизвестного населения или отсутствующего поля `country`.

Клиент показывает фиксированное безопасное сообщение для нового кода;
произвольный текст ошибки сервера не передаётся пользователю. Общий лимит
остаётся прежним: один прикладной MCP-вызов и не более двух LLM-запросов для
чтения. Автоматических повторов HTTP, MCP или LLM нет.

## Внешний отказ и диагностика

Сообщение «Внешний сервис сейчас недоступен» означает HTTP-отказ или ошибку
соединения. Скриншот не позволяет определить, отказал геокодер или погодный
endpoint. Проверка настоящим `WeatherService` 19 октября 2026 года получила
успешные ответы обоих endpoint для `Ростов-на-Дону`. Прежний сетевой отказ не
воспроизведён; эта проверка не гарантирует постоянную доступность Open-Meteo.

Для следующего отказа в stderr добавлена ограниченная диагностика, например:

```text
WARNING weather phase=current code=UPSTREAM_ERROR http_status=503 error_type=_FetchError
```

Значение `phase=geocoding` относится к поиску города, `phase=current` — к
получению наблюдения. При сетевой ошибке без HTTP-ответа `http_status=None`.
Логи не содержат названия города, URL, ответа HTTP, текста исключения или
traceback. stdout дочернего процесса остаётся только транспортом MCP.

## Проверки

Регрессии используют захваченный публичный ответ и подменённый HTTP: повторяющиеся
подписи, уточнение региона, маленькие населённые пункты, повреждённые данные,
HTTP 403/429/503, сетевые ошибки, общий тайм-аут и отсутствие повторов.
Отдельная проверка прогоняет безопасную диагностику через настоящий фильтр
логирования stdio-сервера. Новый код проверен Pydantic, JSON Schema и клиентом MCP.

Полный протокол проверок, включая PostgreSQL:
[`weather-fix-checks.json`](evaluation/weather-fix-checks.json).
Прошли 1179 тестов без пропусков и все 28 критериев ЛР2; зависимости,
Ruff и форматирование проверены. Миграции и исходный набор эксперимента сохранены.
Реальная квота OpenRouter при исправлении не использовалась.

Повторные регрессии коротких названий используют захваченные ответы Москвы и
Ростова, проверяют полные названия, явную страну/регион, границы слов, разные
дефисы и отсутствие выбора по населению или порядку. Изолированная проверка
`tests/test_weather.py` после этого изменения: 129 тестов прошли. Промпт модели,
схемы инструмента и число разрешённых вызовов не менялись.

Описание полей первичного источника:
[Open-Meteo Geocoding API](https://open-meteo.com/en/docs/geocoding-api).
