## 1. Назначение и границы

Существующий Telegram-бот получает текущую погоду, читает обезличенное расписание
и сохраняет подтверждённые напоминания через собственный MCP-сервер по `stdio`.
Инструменты доступны только в `/study`; `/translate` и `/quiz` сохраняют функции ЛР1.
Отправка уведомлений в назначенное время относится к ЛР3 и сюда не входит.
Публичный порт, университетский аккаунт и отдельный постоянно доступный сервер не нужны.
Модель остаётся бесплатной: `nvidia/nemotron-3-super-120b-a12b:free`; платного fallback нет.

## 2. Наблюдаемые пользовательские сценарии

| Запрос или команда | Наблюдаемый результат |
|---|---|
| «Объясни list и tuple» | Один ответ модели; ни одного MCP-вызова |
| «Какая сейчас погода в Казани?» | Значения из `get_weather`, место и время наблюдения; источник указан |
| «Погода в одноимённом городе» | Различимые варианты страны/региона и уточнение; первый результат не выбирается |
| «Покажи занятия завтра» | Дата вычислена по доверенному времени и зоне; занятия либо явное отсутствие занятий |
| «Расписание на текущую неделю» | Чтение `schedule://current-week`; даты понедельника–воскресенья и зона расписания |
| «Напомни завтра в 18:30 отправить отчёт» | При заданной зоне — карточка точных параметров с кнопками; записи напоминания ещё нет |
| То же без сохранённой зоны | Просьба задать `/timezone`; локальное время не интерпретируется моделью |
| «Напомни вечером про лабораторную» | Уточнение даты/времени; подготовленного действия и записи напоминания нет |
| Подтверждение карточки владельцем | Одно напоминание, ответ с его ID, точным временем и IANA-зоной |
| Повтор update или двойное подтверждение | То же подготовленное действие/напоминание; новая запись не возникает |
| Чужая, отменённая или просроченная карточка | Отказ без раскрытия чужих параметров и без записи напоминания |
| Недоступен MCP или погодный сервис | Понятная ошибка; данные и успех операции не выдумываются |

Новый запрос с изменёнными текстом или временем требует новой карточки и нового
подтверждения. Одновременно у пользователя допускается одна действующая карточка:
подготовка новой отменяет предыдущую, повтор того же update возвращает существующую.

## 3. Обнаружение возможностей и решения модели

При запуске MCP-клиент выполняет согласование протокола, получает инструменты с
`inputSchema`, `outputSchema`, описаниями и признаками чтения/изменения, затем список
ресурсов. Разрешены только три имени ниже и URI `schedule://current-week`.
Схемы принадлежат MCP-серверу; Telegram-обработчики их не копируют.
Discovery не считается вызовом пользовательского действия и имеет отдельный тайм-аут.

Основной механизм — нативный tool calling. До его включения отдельно проверяется
поддержка бесплатным endpoint. Допустим настроенный режим строгого структурированного
вывода: схема Pydantic, `extra=forbid`, разбор JSON и программная валидация.
Режим native/structured выбирается до обработки update; автоматическое переключение
после ошибки не допускается, чтобы не расходовать третий запрос модели.
Свободный текст не превращается в команды регулярными выражениями. Если endpoint
не поддерживает ни один проверенный вариант, инструменты отключаются с объяснением;
ошибка не запускает второй вариант автоматически и не вызывает платную модель.

Решение имеет один вариант: `respond`, `clarify`, `call_tool` или `read_resource`.
Для инструментального варианта обязательны разрешённое имя/URI и валидные аргументы.
В native-режиме ресурс представляет клиентский адаптер чтения с URI из discovery;
он вызывает `resources/read` и не добавляет четвёртый инструмент MCP-сервера.
Причина — краткое объяснение действия, пригодное для `/why`, а не цепочка рассуждений.
Несколько вызовов, неизвестное имя, лишние поля, битый JSON или результат маршрутизации
с ограничением длины отклоняются без выполнения и без автоматического LLM-повтора.
Недостающие аргументы требуют уточнения; приложение не подставляет выдуманные значения.

## 4. Строгость общих контрактов

Все объекты ниже запрещают дополнительные поля на каждом уровне. Строки после
удаления крайних пробелов проверяются до выполнения; пустые строки недопустимы,
кроме явно разрешённого пустого `region`.
Даты проходят календарную проверку, числа конечны, время содержит смещение UTC.
Выход каждого инструмента — дискриминированное объединение по `status` с закрытым
набором полей соответствующего варианта; оно публикуется как `outputSchema`.
Результат возвращается в `structuredContent`; текстовая JSON-копия допустима для
совместимости, но не заменяет структурированный результат.

Общий вариант ошибки: `status="error"`, `error={code, message, retryable}`.
`code` — документированное значение из раздела 11, `message` — безопасная строка
1–500 символов, `retryable` — boolean. Ошибка выполнения помечается MCP `isError`;
ошибки протокола/аргументов SDK преобразуются клиентом в тот же внутренний тип.
Несовпадение `structuredContent` со схемой означает ошибку, а не фактический результат.

## 5. Инструмент `get_weather(city)` — чтение

Вход: только `city: string`, 1–100 символов. Страна и регион при уточнении остаются
частью этой строки; координаты, URL и имя провайдера модель передать не может.
Источник — фиксированные геокодирование и погодный API Open-Meteo. Выбор обоснован
доступностью текущих данных и геокодирования без отдельного пользовательского ключа;
актуальные условия и точный формат API проверяются перед реализацией.

| Вариант выхода | Обязательные поля |
|---|---|
| `ok` | `place={name, country, region}`, `temperature_c: number`, `condition={code: integer, description: string}`, `wind={speed: number>=0, unit:"km/h"}`, `observed_at: ISO datetime`, `timezone: IANA string`, `source:"Open-Meteo"` |
| `not_found` | `query: string`, `source:"Open-Meteo"` |
| `ambiguous` | `query: string`, `candidates: array[2..5]` объектов `{name, country, region}`, `source:"Open-Meteo"` |
| `error` | Общий вариант ошибки |

`name` и `country` — строки 1–100, `region` — 0–100; описание условий — 1–200.
Кандидаты различаются названием страны и административной области; если этого
недостаточно, сервер просит более точное место вместо самостоятельного выбора.
Пустой поиск и неоднозначность — корректные доменные результаты, а не HTTP-успех
с выдуманной погодой. Ответ содержит только полученные наблюдения, не прогноз.
Open-Meteo может опускать пустое название страны: в этом случае `country`
содержит проверенный `country_code` источника. Отсутствие названия у одного
кандидата не отвергает весь поиск и не разрешает автоматически выбрать другой.
Разные GeoNames ID могут иметь одинаковые доступные подписи. Для `ambiguous`
объединяются только подписи кандидатов; сами места остаются разными. После
уточнения страны/региона погодный запрос разрешён только при одной локации.
Если у всех найденных мест одна подпись, возвращается `AMBIGUOUS_PLACE` с
фиксированным уточнением клиента, а не `INVALID_ARGUMENTS` и не выбором первого ID.
Отказы HTTP диагностируются по этапу `geocoding`/`current`, коду, HTTP-статусу
и классу ошибки, без запросов пользователя, URL, HTTP-тел или traceback.

## 6. Инструмент `get_schedule(date)` — чтение

Вход: только `date: string`, строго `YYYY-MM-DD`, существующая дата 2000–2100 годов.
Выход `ok`: `date`, `timezone: IANA string`, `lessons: array[0..32]`,
`source:"local_schedule"`. Занятие содержит ровно `start`, `end`, `title`, `location`:
время `HH:mm` в зоне расписания, начало раньше конца в пределах дня;
название 1–200 символов, место 1–100. Занятия отсортированы по началу.

Вне объявленного покрытия: `status="outside_coverage"`, `date`, `coverage_start`,
`coverage_end`, `timezone`, `source:"local_schedule"`. Ошибка файла — общий `error`.
`ok` с пустым `lessons` означает известный свободный день; вне покрытия нельзя
утверждать отсутствие занятий.
Путь к JSON задаёт только конфигурация. Файл содержит покрытие, IANA-зону и расписание
минимум на две последовательные недели, включая явно пустые дни, без ФИО и контактов.
Начальная демонстрационная фикстура покрывает 12–25 октября 2026 года и пригодна
для фиксированной даты обязательного эксперимента; вне её покрытия это явно указано.
Полный файл валидируется при загрузке; произвольные пути из сообщений запрещены.

## 7. Ресурс `schedule://current-week` — только чтение

Ресурс обнаруживается через MCP и читается стандартной операцией `resources/read`.
JSON с MIME `application/json` содержит `week_start`, `week_end`, `timezone`,
`source:"local_schedule"`, `days` из семи объектов по датам в порядке понедельник–воскресенье.
Каждый день содержит `date` и либо `status="ok", lessons`, либо
`status="outside_coverage"`; формат занятия совпадает с инструментом.
Частичное покрытие видно по отдельным дням, отсутствие файла возвращает ошибку.
Неделя определяется по внедряемым часам и настроенной зоне расписания,
а не системной локальной зоне и не предположению модели. Записи через ресурс нет.
При чтении ресурс валидируется общей с сервером строгой моделью результата;
MCP не требует для ресурса инструментального `outputSchema`/`structuredContent`.

## 8. Инструмент `add_reminder(text, remind_at)` — изменение

Вход модели содержит ровно `text: string[1..500]` и `remind_at: ISO datetime`.
Дата-время содержит явное смещение; момент строго позже доверенного текущего времени
как при подготовке, так и при подтверждении. Пользовательская IANA-зона сохраняется
отдельно; показанный локальный момент и смещение должны ей соответствовать.
Модель не получает поля владельца, ключа идемпотентности или авторизации.

Выход `ok`: `reminder_id: UUID`, `remind_at: ISO datetime` в нормализованной зоне,
`timezone: IANA string`, `created: boolean`. Первый commit возвращает `created=true`,
повтор уже выполненного действия — тот же ID и момент, `created=false`.
Другой выход — общий `error`; неуспех никогда не означает «напоминание создано».

Вызов разрешён только для подтверждённого действия. Приложение передаёт вне
аргументов модели доверенный контекст: `action_id` и одноразовую capability из
криптографически случайных 256 бит. Канал — `_meta["labbi/action-capability"]`
с объектом `{action_id, capability}`; сама `_meta` не является доказательством доверия.
Для SDK 2.3.0 проверены `Client.call_tool(..., meta=...)` и серверное `params.meta`.
В PostgreSQL хранится только хеш capability, привязанный к действию, владельцу,
каноническим аргументам и сроку действия. Сервер проверяет хеш, состояние, срок,
совпадение аргументов и выводит владельца из строки действия, созданной по Telegram update.
Самостоятельно переданный `user_id` не даёт полномочий; лишнее поле отклоняется.
Отсутствующий/неверный контекст независимого клиента даёт отказ без записи.
Секрет не попадает в callback-data, модель, `/why`, журнал или сохранённый tool result.
Для уже committed действия после проверки прежней capability и совпадения параметров
возвращается квитанция до проверки будущего времени и TTL: это не новая запись.
Проверки срока, `confirmation_epoch` и будущего момента обязательны для нового изменения.
Право выпускается доверенным сервисом только после принятия callback владельца;
сырой секрет нужен в памяти для конкретного вызова, в БД остаётся хеш. После
перезапуска повторный callback сначала проверяет квитанцию. Если её нет, то же
неотменённое действие в пределах исходного срока может получить новую capability
под блокировкой строки: `action_id`, параметры и срок не меняются, старое право
отзывается. Проверка capability и условий записи выполняется сервером под той же
блокировкой, что и commit; устаревшая проверка не разрешает позднюю запись.

## 9. Подтверждения, повторы и хранение

Состояния действия: `pending` → `approved` → `committed`; также терминальные
`cancelled`, `expired`, `failed`. `approved` означает принятый доверенный callback,
а не создание напоминания. Ошибка доставки ответа Telegram состояние не откатывает.
Общий срок `pending`/`approved` — 300 секунд с подготовки по часам БД,
без продления при подтверждении или повторах.
Подтверждение принимается только от владельца, в том же личном чате и до истечения.
Состояние и отдельный счётчик `confirmation_epoch` пользователя проверяются
транзакционно. Этот счётчик меняется при новой карточке, отмене, `/stop`, `/reset`,
смене режима и зоны. Обычная переписка и температура его не меняют.
Существующий `labbi_users.revision` растёт при каждом сохранении ответа, поэтому
он защищает запись диалога, но не является версией действительности карточки.
Завершённая карточка не даёт нового полномочия, но повторный callback возвращает
сохранённый результат.

Уникальность `(user_id, telegram_message_id)` защищает подготовку и повтор обработки
одного сообщения; уникальность `action_id` у напоминания защищает запись.
Реестр обработанных сообщений хранится отдельно от очищаемой истории и переживает
`/reset`/смену режима: старый update не создаёт новое действие после удаления переписки.
Переход состояния, вставка напоминания и сохранение результата выполняются атомарно
под блокировкой строки действия/ограничениями PostgreSQL. Конкурентные подтверждения
получают один ID. Сетевые вызовы не удерживают соединение или транзакцию БД.
Подготовка действия и сохранение пары вопрос–карточка выполняются одной транзакцией
с проверкой ревизии диалога. Смена `confirmation_epoch` и проверки перед commit
следуют одному порядку блокировок: пользователь, затем его действие.
После неопределённого результата commit приложение сверяет действие и напоминание
в PostgreSQL: не повторяет генерацию/запись вслепую и не сообщает успех без доказательства.
Пока исход операции не установлен, ответ сообщает неопределённость и предлагает
проверить состояние повторным нажатием; оно сначала читает сохранённый результат.
Неизвестный исход отражается отдельным статусом аудита `OUTCOME_UNKNOWN`,
но не переводит действие в `failed` без подтверждения результата транзакции.

Новые миграции добавляют часовую зону и `confirmation_epoch` пользователя, действия/подтверждения,
напоминания и события аудита. Применённые миграции `001`–`005` не меняются.
Напоминание хранит владельца, действие, текст, момент UTC и IANA-зону; подтверждение
также хранит исходное сообщение, срок, состояние, `confirmation_epoch` и канонические параметры.
Все пользовательские запросы хранилища фильтруются по доверенному владельцу.
В `labbi_messages` остаются только пары `user`/`assistant`; служебные tool-сообщения
не меняют существующий CHECK. Квитанция callback хранится в действии/аудите, без
фиктивной пользовательской пары с ID сообщения бота; `/why` отражает итог callback.

## 10. Время, команды и отмена

Пользовательские карточки, квитанции, `/timezone` и `/why` показывают даты в виде
«20 октября 2026, 19:00 (UTC+03:00)», с сохранением ненулевых секунд и микросекунд.
IANA-зона остаётся явной; SQL, MCP и технический контекст используют прежний ISO.

`/timezone <IANA>` проверяет `zoneinfo`, сохраняет зону и показывает текущее время
в ней; без аргумента показывает настройку и время либо её отсутствие. Поставка `tzdata`
обеспечивает одинаковое поведение Linux/macOS/Windows; фиксированное `+03:00`
не заменяет IANA-имя. Неизвестная зона отклоняется без изменения настройки.

Без аргумента `/timezone` открывает меню с текущей настройкой и поиском. Город
или страна в аргументе запускают только поиск; зона сохраняется после выбора
варианта и кнопки «Использовать этот пояс». Страны берутся из tzdata и CLDR
(Babel 2.18.0, 43 локали), города — из фиксированного Open-Meteo geocoding API.
Пользователь или модель не задают URL. Поиск не вызывает LLM/MCP, имеет лимит
15 секунд, 256 КиБ и до 50 вариантов без автоматических повторов. Название страны,
которое совпадает со старым tz-алиасом, не вызывает скрытой смены настройки.
Состояние меню изолировано по владельцу, ограничено по количеству и сроку
десять минут. Новые варианты меняют случайный callback-token; выбранный индекс
проверяется повторно, а старый результат HTTP не заменяет новый выбор.
Просмотр и поиск не отзывают право записи напоминания. Сброс, смена режима и
`/stop` очищают меню; только фактическое сохранение другой зоны отзывает действия
прежнего `confirmation_epoch` через существующую транзакцию.
Локальные напоминания и относительные «завтра/через два часа» требуют сохранённой
зоны; модель не выводит её из языка, города или профиля. Неоднозначное/несуществующее
локальное время DST требует уточнения; бот не выбирает смещение самостоятельно.
Относительные даты занятий и неделя вычисляются в настроенной зоне расписания
(`Europe/Moscow` для фикстуры), явно переданной модели. Ответ показывает дату/зону.

Явная просьба создать напоминание проверяется локально до LLM: без сохранённой
зоны, даты или точного времени возвращается уточнение. Дата и время берутся
только из связанных пользовательских реплик; предложения ассистента не считаются
выбором пользователя. Для полного запроса structured-схема допускает только
подготовку `add_reminder` либо уточнение. Свободный текст модели не заменяет
карточку и не подтверждает запись; предложенное время сверяется с просьбой.
Эквивалентный момент модели в UTC приводится к сохранённой IANA-зоне только
после такой сверки; будущее время, DST и смещение нормализованных параметров
проверяются прежним валидатором.
Неоднозначные или неподдержанные формулировки требуют явной даты и времени.
Текстовое «да» при действующей карточке локально направляет к кнопке владельца,
без новой карточки, LLM, MCP и смены `confirmation_epoch`.

`/tools` показывает обнаруженные имена, описания, чтение/изменение и необходимость
подтверждения; при отказе MCP сообщает недоступность. `/start` включает новые команды.
`/why` читает последнее событие только текущего владельца: время, действие, имя,
безопасное резюме аргументов, проверка, выполнение и короткая причина.
При отсутствии событий сообщает об этом; не раскрывает prompt, токены и рассуждения.

`/stop` отменяет активную обработку, ожидающие запросы и ещё не выполненное
действие пользователя (`pending` или `approved`). `/reset` и смена режима делают
то же до своей операции. Смена зоны отменяет прежнее ещё не выполненное действие,
чтобы время нельзя было подтвердить по устаревшей настройке. Отзыв прав и проверка
сервером согласованы блокировкой строки действия. Уже committed напоминание команды не удаляют;
при гонке итог определяется транзакционно и сообщается по фактическому состоянию.

## 11. Пределы, ошибки и недоверенные данные

Telegram-карточка после committed/cancelled/expired удаляется только после
доставки итогового сообщения. Разрешение даёт типизированный признак результата
сервиса подтверждений, не текст модели. При unknown/error или ошибке доставки
карточка остаётся. Неуспех удаления не откатывает запись: приложение пытается
убрать кнопки, не выполняя повторный MCP-вызов.

Пользователь согласовал: обычный ответ — максимум **1 LLM, 0 MCP**; чтение —
максимум **2 LLM, 1 MCP**; подготовка напоминания — максимум **1 LLM, 0 MCP**;
подтверждающий callback — **0 LLM, 1 MCP** с детерминированной квитанцией.
Один MCP-вызов — `tools/call` или `resources/read`; отказ также расходует бюджет.
Второй LLM получает результат чтения с источником и отключёнными инструментами.
В native-контексте сохраняются `assistant.tool_calls`, соответствующий `tool` и
совпадающий call ID; в structured-режиме — отдельный маркированный контейнер данных.
Этот временный контекст строится отдельно от строковых пар `build_context` ЛР1;
схемы, аргументы и результат входят в бюджет контекста 6000 токенов по оценке приложения.
Новых действий, циклов продолжения, повторной маршрутизации и авто-продолжений нет.
Превышение лимита останавливает обработку и создаёт событие аудита; установленный
предел 1 MCP строже максимума методички 2 MCP на сообщение.

Пределы по умолчанию: 60 секунд на LLM-вызов, 2048 output tokens (как ЛР1),
135 секунд на всю обработку, 15 секунд на MCP/discovery; HTTP-чтение укладывается
в этот дедлайн. Автоматических повторов LLM, прикладного MCP-вызова и погодного
HTTP-чтения нет. Результат MCP ограничен 32 КиБ, файл расписания — 1 МиБ.
Настройки: `SCHEDULE_FILE=data/schedule.json`,
`SCHEDULE_TIMEZONE=Europe/Moscow`, `MCP_TIMEOUT_SECONDS=15`,
`AGENT_TIMEOUT_SECONDS=135`, `LLM_TOOL_MODE=structured` (также доступен `native`).
Исходный structured выбран до обработки по каталогу текущего бесплатного endpoint:
на 18.10.2026 `supports_tool_choice.none=false`; строгий JSON поддерживается.
Это повторно подтверждено [каталогом 19.10.2026](docs/evaluation/lab2-provider-evidence.json).
В structured-финале `tools=[]`, в native-финале исходные схемы и `tool_choice=none`.
Отказ не вызывает переключение режима и повторную генерацию; подробности —
[документ этапа 4](docs/lab2-agent.md#почему-по-умолчанию-structured).
Зона файла обязана совпадать с `SCHEDULE_TIMEZONE`; несовпадение — ошибка источника.
Эти поля уже проверяются `Settings` и описаны в `.env.example`.
MCP SDK 2.3.0 и зависимости закреплены на этапе 2; MCP-клиент и агент этапа 4
реализуют дедлайны и пределы вызовов. Лимиты проверяет код, не модель.
Пределы 1 MCP/2 LLM являются жёсткими верхними границами и не повышаются настройками.

Безопасные коды ошибок: `INVALID_ARGUMENTS`, `UNKNOWN_TOOL`, `UNAUTHORIZED`,
`CONFIRMATION_REQUIRED`, `ACTION_CANCELLED`, `ACTION_EXPIRED`, `ACTION_CONFLICT`,
`TIMEZONE_REQUIRED`, `AMBIGUOUS_TIME`, `AMBIGUOUS_PLACE`, `MCP_UNAVAILABLE`, `TIMEOUT`,
`UPSTREAM_ERROR`, `INVALID_RESULT`, `SOURCE_UNAVAILABLE`, `CALL_LIMIT`, `OUTCOME_UNKNOWN`.
При отказе итогового LLM после чтения — краткая детерминированная передача проверенных
данных с источником или честная ошибка, без нового LLM-запроса. Частичный обычный
текст ЛР1 сохраняется с предупреждением; частичное решение на запись не исполняется.
Старые локальные проверки чрезмерного объёма и уточнение темы эссе сохраняются.

Текст инструмента — данные, а не инструкции. Ни пользователь, ни модель не задают
путь, URL, SQL, команду ОС или произвольное имя функции. MCP получает минимальное
окружение без Telegram/OpenRouter-секретов; stdout предназначен только протоколу.
Аудит в БД содержит время, владельца, request ID, действие, безопасные аргументы,
статусы и длительность; текстовый лог — случайный request ID и технические статусы,
без Telegram ID, username, полного текста, секретов и системных инструкций.
Просьба о зонте «сегодня» допускает вывод только о текущем наблюдении: без прогноза
нельзя уверенно обещать погоду на весь день. Источник не меняет инструкции агента.

## 12. Приёмка и воспроизводимая проверка

Сохраняются тесты ЛР1. Новые unit-тесты подменяют Telegram, LLM, погоду и часы.
Обязательны точные проверки успеха/неуспеха каждого инструмента, пустого дня,
покрытия, ложных дат/зон, DST, отсутствия зоны, подтверждения, отмены и истечения.
Проверяются неизвестный инструмент, лишние поля, ограничение вызовов, отказ MCP,
битый результат/API, инъекция в tool result, запрос секретов, чужие действия и `/stop`.
Недоступность MCP не мешает обычным ответам. Ошибка Telegram не создаёт второй записи.
На реальном PostgreSQL повтор update и конкурентные callbacks дают одну подготовку
и одно напоминание; перезапуск сохраняет зону, pending, результат и аудит.
Независимый MCP-клиент обнаруживает три инструмента/ресурс и читает данные;
изменение без capability в рабочей конфигурации отклоняется. Разрешённое изменение
в Inspector проверяется только с тестовой идентичностью и отдельной тестовой БД.

Эксперимент использует неизменённый [набор 12 запросов](docs/evaluation/lab2-routing.json),
часы `2026-10-12T09:00:00+03:00`, зону `Europe/Moscow`. Внутри каждого прогона
модель и настройки неизменны. Новое сравнение двух бесплатных моделей и температур
фиксирует общий промпт и меняет только model/temperature по предварительно
сохранённому [протоколу](docs/evaluation/lab2-comparison.md).
Три напоминания оцениваются по подготовленному действию без фактической записи.
`routing_accuracy >= 10/12`, `argument_accuracy >= 8/9`; пропущенный нужный вызов
не удаляется из знаменателя. Сохраняются все исходные и фактические результаты.
Для ошибок меняется один элемент решения и повторяются ошибочные кейсы с сохранением
обоих результатов. Дополнительные примеры не заменяют обязательные двенадцать.
Итоговая приёмка требует документации, инструкции запуска и защиты, чистых от секретов
данных, успешных проверок, реального независимого MCP-клиента и тега `lab2`.

## 13. Источники протокольных решений

[схемы и результаты инструментов](https://modelcontextprotocol.io/specification/2025-11-25/server/tools),

Наличие `_meta` предусмотрено протоколом; проверка capability и связь с действием —
наше прикладное решение, реализованное и проверенное на этапе 3. Подготовка
действия из Telegram и выпуск capability реализованы на этапе 5; проверки
конкурентных подтверждений и восстановления после отказов завершены на этапе 6.
Контракты погодного адаптера сверяются с [Open-Meteo](https://open-meteo.com/en/docs)
и [геокодированием](https://open-meteo.com/en/docs/geocoding-api).
