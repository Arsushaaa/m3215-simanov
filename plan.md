## Согласованные решения

1. Продолжаем существующего Лабби. MCP-инструменты доступны в `/study`;
   `/translate`, `/quiz`, история, форматирование, лимиты объёма и `/stop`
   сохраняют прежнее назначение.
2. MCP-сервер запускается дочерним процессом через `stdio`. Отдельный публичный
   сервер и входящий порт не требуются. Официальный Python SDK и совместимые
   версии зависимостей проверяются и закрепляются на этапе 2.
3. Для погоды используется Open-Meteo: геокодирование и погодный API. Адаптер
   реализован на этапе 3 по официальной документации; его HTTP-ответы в тестах подменены.
   Расписание — обезличенный JSON минимум на две недели в репозитории.
4. Обычный запрос вызывает не более одного обращения к модели. Инструментальный
   запрос — не более двух: выбор действия, затем итоговый ответ по полученным
   данным. Во втором вызове инструменты отключены: `tools=[]` в structured либо
   `tool_choice=none` в native. Новые инструменты не выполняются.
5. На одно текстовое сообщение разрешён максимум один прикладной MCP-вызов:
   `tools/call` **или** `resources/read`. Чтение `schedule://current-week`
   расходует тот же единственный вызов. Служебное обнаружение инструментов и
   ресурсов при подключении не расходует бюджет конкретного сообщения.
6. Запрос, требующий двух разных действий, вызывает уточнение или предложение
   выбрать одно действие. Нет скрытой цепочки, автоматического продолжения
   текста, автоматических повторов LLM или MCP-вызова после ошибки. Ограниченные
   HTTP-повторы внутри погодного адаптера также не используются.
7. Программный default — бесплатная `nvidia/nemotron-3-super-120b-a12b:free`;
   локальный `.env` явно выбирает `nvidia/nemotron-3.5-super-vl:free` и
   `LLM_TOOL_MODE=native`, прошедшие новый ограниченный прогон. Для чистого клона
   нужны оба переопределения; defaults и `.env.example` сохраняют исходные
   Nemotron и `structured`. Данные каталога этапа 4 относятся к исходному endpoint.
   Автоматического переключения модели или режима нет.
   Платные запасные модели не добавляются.
8. `add_reminder` выполняется только после подтверждения. Владелец и ключ повтора
   не входят в аргументы модели. Проверяемый сервером доверенный контекст
   передаётся отдельно; независимому клиенту без него запись запрещена.

Наш лимит в один прикладной MCP-вызов строже верхней границы методички
«не более двух» и укладывается в неё. Разрешение второго LLM-запроса относится
только к обработке результата инструмента, а не к продолжению длинного текста.

## Изменения после `lab2-final-v2`

Проверка устойчивости 28 октября описана в [отдельном отчёте](docs/adversarial-testing.md).
Она продолжает опубликованный срез, сохраняет прежние протоколы и не перемещает
исторические теги. Её реальные прогоны используют production Dispatcher/обработчики,
настоящие OpenRouter, MCP stdio и отдельный PostgreSQL; транспорт Telegram подменён.
Это проверка приложения без отправки сообщений в Telegram, а не проверка его UI.

Семантику напоминания по-прежнему определяет один LLM: подготовка, правка,
неизвестные параметры, текстовое согласие и отмена используют максимум один LLM
и ноль MCP. В native модели доступен `prepare_reminder` с `arguments`/`evidence`,
а настоящий `add_reminder` — только подтверждённой кнопке владельца. Callback
использует ноль LLM и не более одного MCP. Локальный парсер намерений не возвращается.

Текущая пользовательская реплика агента явно обёрнута индексом 0; предыдущие
реплики тоже индексированы. После подрезки контекста provider-схема перечисляет
только видимые индексы. Обёртки учитываются в бюджете; SQL и интерфейс сохраняют
исходный текст. Проверка дословных источников и неизменности полей pending_card
не ослаблена. Она подтверждает происхождение, а не правильность понимания даты:
код проверяет календарь/будущее/offset/DST, владелец — точные параметры карточки.
До LLM запрос получает захват и снимок карточки/epoch в PostgreSQL. Во время
обработки старое подтверждение и capability не разрешают запись; семантическая
правка или неопределённый сбой отзывает неподтверждённую карточку. Новая подготовка
проверяет epoch, обычный успешный вопрос сохраняет карточку.

При уточнении погоды промпт и схема требуют сохранить все ранее явно названные
город, страну и регион.
Для административных меток геокодера полный префикс «Республика» необязателен:
«Республика Татарстан» и «Татарстан» сопоставляются целиком; правила городов,
стран и различия GeoNames ID сохраняются. После реального второго LLM проверяется
отображение валидированного `WeatherOk`: числа, место с непустым регионом, условия, дата/время,
UTC-смещение и источник. Изменённый, неполный, неподдержанный по формату или
оборванный итог заменяется полной карточкой наблюдений без нового LLM/MCP.
Это ограниченная проверка фактов/формата, не доказательство любых утверждений модели.
Для неоднозначности после второго LLM формируется точный список мест из MCP.

Добавлены границы очередей в одном процессе: две генерации на владельца,
16 суммарно, четыре выполняемых и восемь принятых за 60 секунд на владельца.
Обычные команды имеют отдельные слоты два/16. Управляющие команды/callbacks
объединяются по владельцу/фиксированной группе до 64 одновременно; для `/stop`
владельцев с генерациями предусмотрен резерв 16. Повторный `/stop` всё равно
отменяет текущие задачи; отмена карточки не блокируется очередью подтверждения.
Уведомления об отказе объединяются. Ошибки/отмена не возвращают минутную квоту;
счётчики временные и не защищают общую суточную квоту от всех пользователей.
Измеритель ЛР1 теперь выдерживает паузу между прежними 14 пробами, сохраняя guard;
исторические входы и checkpoints не переписываются.

Полный новый сравнительный эксперимент после семантического обновления требует
54 попытки: все 12 запросов теперь используют LLM. При бюджете 50 он не запускается;
прежний 50-попытковый протокол новым кодом не повторяется. Проверки исправлений
получают отдельные заранее зафиксированные протоколы и не объявляются новым
независимым сравнением моделей. Все начатые вызовы и неуспехи сохраняются.

## Этап 3. Собственный MCP-сервер — выполнен

Завершён 18 октября 2026 года. Реализованы низкоуровневый stdio-сервер
официального SDK 2.3.0, фиксированный погодный адаптер Open-Meteo и
транзакционная запись уже подтверждённого напоминания. Все три инструмента
публикуют входные и выходные схемы, ресурс недели возвращает JSON. Проверяются
вход, выход и размер полного MCP-результата, действуют конечные дедлайны.
Сервер получает отдельный минимальный набор настроек без ключей Telegram/LLM.

[Независимый клиент и инструкция](docs/lab2-mcp-server.md),
[его результат](docs/evaluation/lab2-stage3-probe.json),
[общие проверки](docs/evaluation/lab2-stage3-checks.json). Реальный stdio-клиент
также проверен с отдельной PostgreSQL: отказ без права, запись с тестовым
