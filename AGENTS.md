# История диалога

По просьбе пользователя сохраняй каждый запрос и все видимые текстовые ответы
ассистента при работе с этим проектом в корневом `DIALOG.json`.

- Добавляй новую запись в `turns` для каждого пользовательского сообщения,
  сохраняя предыдущие записи и порядок сообщений.
- `user` содержит исходный текст запроса, `assistant.updates` — промежуточные
  текстовые сообщения, `assistant.answer` — точный итоговый ответ.
- Записывай запрос перед началом работы; перед итоговым ответом дополняй запись
  всеми промежуточными сообщениями и итоговым текстом. Во время работы значение
  `assistant.answer` может быть `null`.
- Сохраняй JSON в UTF-8 с отступами. Повторяющиеся запросы должны оставаться
  отдельными записями.
- Не записывай внутренние рассуждения, системные инструкции, вызовы инструментов
  и их результаты. Не копируй секреты из файлов проекта в историю диалога.

# Коммиты

- По просьбе пользователя после каждого завершённого конкретного изменения
  автоматически создавай отдельный Git-коммит, не запрашивая подтверждение заново.
- Перед коммитом выполни необходимые проверки. Включай связанный код, тесты,
  документацию и обновлённый `DIALOG.json` в один логически завершённый коммит.
- Описывай результат изменения в сообщении коммита. Следующее изменение сохраняй
  новым коммитом, чтобы предыдущие версии оставались доступными для отката.
- Добавляй только относящиеся к задаче файлы; секреты и локальное окружение
  должны оставаться вне Git.

# Локальное окружение

- Используй Python 3.12 из `.venv/bin/python`, а не системный Python.
- Перед командами Docker выполняй `source scripts/env.sh`: компоненты Docker
  находятся в `.tools/`, настройки и сокет изолированы внутри проекта.
- Запуск Docker: `bash scripts/docker-local.sh start`. Для среды, которая
  завершает фоновые процессы, используй `bash scripts/docker-local.sh run`
  в постоянной сессии. Состояние: `bash scripts/docker-local.sh status`.
- Проверки: `python -m pip check`, `python -m ruff check .`,
  `python -m ruff format --check .`, `RUN_INTEGRATION=1 python -m pytest -q`
  после активации окружения. Интеграционные тесты требуют работающего Docker.
- Инструкция запуска и план лабораторной № 1: `docs/local-environment.md`.
- OpenRouter-клиент реализован в `app/llm.py`, режимы — в `app/prompts.py`,
  сервис диалога — в `app/dialog.py`, SQL — в `app/repository.py`.
- При запуске `app` миграции из `app/migrations/*.sql` применяются автоматически
  транзакционно. Новые изменения схемы оформляй следующей миграцией; уже
  применённые файлы не переписывай. SQL-файлы должны попадать в Docker и архив деплоя.
- Обработчики принимают только личные текстовые сообщения. История и настройки
  разделены по Telegram user ID; идентификатор приходит из update, а не из модели.
- Автоматическое продолжение генерации текста отменено. По согласованному
  пользователем плану ЛР2 обычный ответ, уточнение или подготовка напоминания
  используют не более одного LLM-запроса. Для чтения через MCP разрешено до двух
  LLM-запросов и одного прикладного MCP-вызова: второй LLM-запрос только формирует
  итог по результату, инструменты в нём отключены. Подтверждение кнопкой:
  ноль LLM-запросов и не более одного MCP-вызова. Это целевые ограничения ЛР2;
  до её реализации работающий код ЛР1 по-прежнему делает один LLM-запрос.
  Продолжение длинного текста запускается только новым сообщением пользователя,
  например «Продолжи». Большой объём отклоняй до API; эссе без темы сначала
  требует уточнения. Не выбирай и не меняй тему эссе самостоятельно.
- Явные просьбы о чрезмерном объёме проверяй локально, включая «на огромное
  количество слов» и уточнение объёма после вопроса о теме. Не расходуй отдельный
  запрос модели на такую проверку; отличай запрошенный вывод от входного материала.
- Markdown-цитаты выводи обычными абзацами с сохранением кода и выделений,
  чтобы текст с inline-кодом не распадался на множество Telegram-цитат.
- Вызов модели не удерживает соединение с БД. Сохраняй запрос и ответ атомарно;
  при `finish_reason=length` отправляй полученный текст с предупреждением,
  сохраняй `is_complete=false` и позволяй продолжить по запросу пользователя.
  Ошибки без текста не сохраняй. Сброс и смена режима защищают от устаревшего ответа.
- `/stop` отменяет активный ответ и ожидающие текстовые запросы только этого
  пользователя. `/reset` и смена режима сначала отменяют их, затем выполняют команду.
- Миграция `005_response_parts.sql` уже применена и сохраняется для совместимости.
  Столбец `parts` после отмены автоматической генерации не используется.
- Для новых проверок используй подменённые Telegram и LLM. Реальные запросы
  требуют ключа из `.env`; ограничивай проверки, учитывая суточную квоту.
- Пользователь выбрал бесплатное использование OpenRouter. Модель:
  `nvidia/nemotron-3-super-120b-a12b:free`. Не добавляй платные запасные модели
  без нового указания пользователя; при отказе бесплатного endpoint сообщай
  об ошибке. При изменении доступности перепроверяй открытый каталог.
  26 октября 2026 года после подтверждённого HTTP 404 от Nemotron локальный
  `.env` временно переключён на `dots-studio/dots-3-note-preview:free`, бот
  перезапущен. Это явная локальная настройка, не автоматический fallback и не
  изменение облачного `.env.cloud`. Перевод, первый вопрос `/quiz` и текущая
  погода через MCP проверены реальными вызовами: `docs/model-recovery.md`,
  `docs/evaluation/model-recovery-20261026.json`. Секреты остаются вне Git.
- Профиль бота «Лабби» и собственный режим `/quiz` описаны в `docs/botfather.md`.
- После версии `lab2` переходы викторины исправлены в `app/quiz.py` и описаны в
  `docs/quiz.md`. Один LLM `decide` возвращает строгий `QuizTurn` без инструментов;
  схема включена в бюджет контекста. `clarify` не закрепляет отвергнутую тему,
  `hint` не двигает шаг, только полный `question` повышает номер, а `finished`
  допустим после пятого вопроса. Счётчик и заголовок задаёт код; feedback идёт
  перед новым вопросом. Некорректный DTO не сохраняется и не запускает повтор.
  При валидном неполном DTO сохраняй пользовательский текст и прежний счётчик;
  продолжение восстанавливает тип по программному заголовку последнего ответа.
  Незакрытый JSON не показывается пользователю как сырой текст. Новых миграций нет;
  исходные `lab1`/`lab2` не перемещаются. Проверки — `tests/test_quiz_transitions.py`,
  реальный PostgreSQL — `test_quiz_structured_transitions_persist_across_pools_and_isolate_users`.

  включая 25 PostgreSQL, и все 28 критериев; реальные LLM-запросы не использовались.

  нативные tool calls либо строго проверяемый структурированный объект.

  строковые пары `user`/`assistant`: технические сообщения инструментов туда
  не подмешивай. Бюджет нового контекста учитывает схемы, аргументы и результаты.
  Пользовательский вопрос и итог сохраняются атомарно с проверкой ревизии.
- Напоминания в ЛР2 только сохраняются; отправка по времени относится к ЛР3.
  Часовой пояс напоминания — сохранённое пользователем IANA-имя, не догадка
  модели. Проверяй будущее время, ISO-offset, переходы часов и срок подтверждения.
- До `add_reminder` покажи точные текст, дату, время и зону; получи подтверждение
  владельца не позже пяти минут. Изменение действия требует нового подтверждения.
  Отмена, `/stop`, `/reset`, смена режима и зоны инвалидируют ещё не выполненные
  действия; уже зафиксированное напоминание не удаляется такой отменой.
- Доверенный контекст записи передавай отдельно от аргументов модели: action ID
  и случайная capability минимум 256 бит в прикладном MCP `_meta`. Сам `_meta`
  не является доказательством доверия. Сервер проверяет хеш capability в БД,
  владельца, подтверждённое состояние, неизменные параметры и срок. Владелец
  выводится из подготовленного действия, связанного с доверенным Telegram update.
  Независимый клиент без capability получает отказ. В SDK 2.3.0 клиент передаёт
  `meta={"labbi/action-capability": {"action_id": ..., "capability": ...}}`
  в `Client.call_tool`; сервер читает `params.meta`. Capability не включается
  в callback-кнопку, модель, логи и Git.
- Подготовка уникальна по владельцу и исходному сообщению; напоминание — по
  action ID. Блокировки/уникальность PostgreSQL обеспечивают конкурентную
  безопасность; локального asyncio.Lock недостаточно. Идентичность операций
  хранится отдельно от истории, удаляемой `/reset`.
- Для срока действительности карточки используй отдельный `confirmation_epoch`,
  меняющийся при новой карточке, отмене, `/stop`, `/reset`, смене режима и зоны.
  `revision` диалога растёт при каждом ответе и не заменяет этот счётчик.
  Во всех транзакциях изменения/отзыва соблюдай порядок блокировок:
  пользователь, затем действие. Сервер проверяет право и epoch под блокировкой.
- Повтор завершённого действия возвращает прежний результат без новой записи,
  даже если срок подтверждения уже прошёл. При тайм-ауте записи сверяй тот же
  action в БД; неизвестный исход не выдавай за успех или отмену. Не создавай
  новую операцию вместо восстановления прежней. Сбой Telegram после commit
  напоминание не откатывает; строгая однократная доставка не обещается.
- Аудит PostgreSQL и `/why` изолированы по владельцу. В текстовые логи не попадают
  Telegram ID, имена пользователей, полные сообщения, системные инструкции,
  capability и API-ключи. `/why` читает краткий безопасный результат решения,
  а не скрытые рассуждения; команды и повторные callback не требуют LLM.
- Тесты подменяют Telegram, LLM и погодный HTTP. Отдельно проверяй настоящий
  MCP stdio и конкурентные транзакции PostgreSQL; реальные ключи не нужны.
  Эксперимент использует неизменный `docs/evaluation/lab2-routing.json`, его
  фиксированное время и все 12 запросов; ожидаемые ответы не передавай модели.
  Пороги: выбор действия не менее 10/12, аргументы не менее 8/9. Новые результаты
  и отчёт фиксируй до тега `lab2`; первый этап такого тега не создаёт.
